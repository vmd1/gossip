# Message Type Registry

This table is the single source of truth for every `type` value that can appear in a Connect wire envelope (see `schema/envelope.schema.json`). Because the Mac app is written in Swift and the Android app is written in Kotlin, there is no shared compiler or shared type definitions between the two codebases — this file is the only thing keeping them in sync.

**Every future feature PR, in either codebase, must add its own `type` entries to this table before shipping.** A message type that isn't registered here should not be sent or handled. Keep `payload fields` precise enough that both sides can implement `Codable` (Swift) / `kotlinx.serialization` (Kotlin) models from this table alone, without needing to read the other language's source.

Wave 1 registers only the message types needed for handshake, presence, and stubbed trust plumbing. Feature message types (e.g. `clipboard.*`, `notifications.*`, `files.*`) are out of scope for this wave and must not be added here until their owning feature is actually being built.

| type | direction | payload fields | description |
|---|---|---|---|
| `handshake.hello` | mac→android / android→mac | `noise` (base64 string, Noise_IK handshake message bytes), `deviceName` (string), `deviceType` (`"mac"` \| `"android-phone"` \| `"android-tablet"`) | First message sent by the initiator to begin a Noise_IK handshake and announce basic device identity. See `docs/adr/0003-noise-ik-handshake.md`. |
| `handshake.ack` | mac→android / android→mac | `noise` (base64 string, Noise_IK handshake response bytes), `deviceName` (string), `deviceType` (`"mac"` \| `"android-phone"` \| `"android-tablet"`) | Responder's reply completing the Noise_IK handshake, carrying its own handshake bytes and device identity. |
| `presence.online` | bidirectional | *(none)* | Sent once a Noise session is established and the sender considers itself actively connected. On Mac this previously silently never sent in practice: called synchronously from `finalizeHandshake`, before the `connectionState` assignment (dispatched via `DispatchQueue.main.async`) had actually taken effect, so `TransportManager.send()`'s old `connectionState`-gated guard always saw the connection as not-yet-connected. Fixed alongside the `dnd.update` initial-sync bug this exact race also caused (see that row) — `send()` no longer gates on `connectionState` at all, only on the actual `noiseSession`/`connection`. |
| `presence.offline` | bidirectional | *(none)* | Sent as a graceful notice that the sender is about to disconnect (app quit, Bluetooth/Wi-Fi teardown, etc). |
| `presence.heartbeat` | bidirectional | *(none)* | Periodic liveness ping/pong used to detect a silently-dropped connection — one `NWConnection`'s own path-viability tracking (Mac) / a blocking socket read erroring on a clean close (Android) doesn't reliably cover: the peer's Wi-Fi dropping, its OS killing/sleeping the process without a clean close, or a NAT/carrier timeout on a cross-network path can all leave a connection sitting at CONNECTED indefinitely with nothing to trigger reconnection. Previously defined but genuinely unused on both platforms — nothing sent it and nothing ran on a timer. Now: while connected, both sides send this every 20s and independently track the last time *any* frame (not just a heartbeat) was received from the peer; if a heartbeat send fails, or more than 3 intervals (60s) pass with nothing received, the connection is torn down and the normal discovery/reconnect loop takes over. See `TransportManager.startHeartbeatMonitoring` (Mac) / `TransportManager.heartbeatLoop` (Android). |
| `trust.roster_update` | bidirectional | `devices` (array of `{deviceId: uuid, publicKey: base64 string, deviceName: string, deviceType: "mac" \| "android-phone" \| "android-tablet"}`) | **Stubbed, unused until multi-device ships.** Reserved shape for gossiping the local trusted-device roster across a device group. No roster-gossip logic is implemented in Wave 1; see `docs/adr/0002-device-group-addressing.md`. |
| `trust.revoke` | bidirectional | `deviceId` (uuid) | Notifies the group that a device's trust/pairing has been revoked and its key should no longer be accepted. |
| `screen.start` | mac→android | *(none)* | **Signaling only** — sent when the Mac begins ADB-mediated screen mirroring (see Wave 2 screen-mirroring unit). The Android side has nothing to actually *do* in response over the transport: mirroring itself is driven entirely by `adb`/`adb exec-out screenrecord` against a local ADB tunnel, not by this message. This exists purely so the Android app's UI can show a "Mirroring active" indicator if it wants to. The mirroring video/input data never goes through Noise encryption or this JSON envelope framing — it flows over a separate `adb`-forwarded channel; see `docs/wire-protocol.md`'s note on large binary payloads for why, and the unit's PR for the full rationale. |
| `screen.stop` | mac→android | *(none)* | Signaling counterpart to `screen.start`, sent when the Mac stops mirroring. Same caveat: purely a UI-state hint, not something the ADB pipeline depends on. |
| `media.nowplaying` | android→mac | `title` (string), `artist` (string), `artBase64` (string, optional, base64-encoded album art image bytes), `isPlaying` (bool), `positionMs` (int), `durationMs` (int), `packageName` (string, the source app's package name) | Sent by the phone whenever its active media session's playback state or metadata changes, so the Mac can render a now-playing UI. `artBase64` is small album-art cover art; per `docs/wire-protocol.md` this is an acceptable exception to the "no base64 blobs" convention only because it is bounded/optional here, not a large binary transfer. |
| `media.command` | mac→android | `action` (`"play"` \| `"pause"` \| `"next"` \| `"previous"`), `seekMs` (int, optional, only meaningful alongside `play`/`pause` as a seek-to-position request) | Sent by the Mac to control playback on the phone's currently active media session. |
| `notification.posted` | android→mac | `id` (string, stable per-notification identifier chosen by the Android sender), `appPackage` (string), `appName` (string), `title` (string), `body` (string), `iconBase64` (string, optional, PNG bytes base64-encoded), `hasReplyAction` (bool, whether the source notification exposes a `RemoteInput`-bearing action the Mac can reply through), `timestamp` (integer, epoch ms) | Mirrors an Android status-bar notification onto the Mac as a local notification. Excludes `MediaStyle` playback notifications (detected via `EXTRA_MEDIA_SESSION`, the same signal the system itself uses) — those are already covered end to end by `media.nowplaying`/`media.command`, which has real transport controls and would otherwise re-post a redundant mirrored copy on every playback tick as the notification's progress updates. |
| `notification.removed` | android→mac | `id` (string, matches the `id` from a prior `notification.posted`) | Tells the Mac to dismiss the previously-mirrored notification (the source notification was cleared or dismissed on Android). |
| `notification.reply` | mac→android | `id` (string, matches the `id` from a prior `notification.posted`), `text` (string) | Carries a Mac-side inline reply back to Android so it can be delivered through the original notification's `RemoteInput`/`PendingIntent`, round-tripping into the real conversation. Only valid for notifications where the matching `notification.posted` had `hasReplyAction: true`. |
| `notification.dismiss` | mac→android | `id` (string, matches the `id` from a prior `notification.posted`) | The reverse of `notification.removed`: the user dismissed the mirrored notification on the Mac, so the original on Android should be cleared too. **Not** driven by `UNUserNotificationCenterDelegate`'s dismiss callback as originally implemented — confirmed directly (unconditional logging at the top of that delegate method, zero deliveries for a swipe-dismissed banner) that macOS does not reliably invoke `didReceive` with `UNNotificationDismissActionIdentifier` for a plain banner swipe/close, unlike iOS. Instead `NotificationMirrorManager` polls `UNUserNotificationCenter.getDeliveredNotifications` every 5s and diffs it against the set of identifiers it's posted and not yet resolved; anything that dropped out of the delivered list without the Mac having removed it itself (i.e. no matching `notification.removed` arrived first) is inferred as user-dismissed. The `didReceive`/`UNNotificationDismissActionIdentifier` path is kept as a fast path in case some interaction or future macOS version does provide it, but the poll is the actual mechanism this depends on. On Android, handled via `NotificationListenerService.cancelNotification(key)`, the same special capability the service grants for snooze/dismiss features — an ordinary app has no way to dismiss another app's notification. This in turn fires Android's own `onNotificationRemoved` and sends `notification.removed` back to the Mac; harmless (no-ops removing an already-removed mirrored notification) since the Mac never reacts to `notification.removed` by dismissing anything itself, so it isn't a ping-pong loop. |
| `dnd.update` | bidirectional | `sourceDeviceId` (uuid), `enabled` (bool), `isInitialSync` (bool, default `false`) | Sent whenever the sender's own Do Not Disturb / Focus state changes, reporting that new state to the peer. Also auto-reconciled: if the reported `enabled` disagrees with the receiver's own last-known/expected state, the receiver applies it locally the same way it would a `dnd.set` (see below) — so toggling either device mirrors onto the other. Both sides track an `expectedState` (last state they reported or applied) and skip re-sending/re-applying when a newly-observed value already matches it, to avoid an infinite update ping-pong — same convention as `clipboard.update`. On Mac, applying a peer-requested change runs a Shortcut, which itself re-triggers the Shortcuts automation that reports local changes (see `dnd.set` row); both sides also apply a short cooldown after applying a peer state before accepting a new local-change report, as a guard against that automation's delivery timing racing the in-memory state update. On Mac, local changes are detected via a user-configured Shortcuts automation calling the `connect://dnd` URL scheme (see `mac/Connect/Features/DND/DNDSyncManager.swift`); on Android via a `BroadcastReceiver` for `NotificationManager.ACTION_INTERRUPTION_FILTER_CHANGED` (see `android/app/src/main/kotlin/com/connect/features/dnd/DndSyncManager.kt`). **`isInitialSync: true`**: sent once by each side on every fresh `CONNECTED` transition (not gated on a local change), carrying that device's real/best-known current state, specifically to reconcile two devices that were apart and may have independently diverged. The receiver does *not* mirror this — it ORs the reported value with its own real/known state and applies the OR'd result if that differs from its own (`enabled=true` wins over `enabled=false` on either side). This must be a merge rather than a mirror: two devices reporting concurrently on connect and blindly mirroring each other would *swap* their states instead of converging. OR is commutative, so both sides converge to the same target independently of message ordering. On Mac (no API to read live Focus state), "real/known state" means the persisted `expectedState` (`UserDefaults`, key `com.connect.app.dnd.expectedState`), defaulting to `false` if genuinely never observed; on Android it's a live `NotificationManager.currentInterruptionFilter` read, always available. **Periodic resync**: both sides also re-send an `isInitialSync` report every 60s while connected (`SyncForegroundService.runDndResyncLoop` on Android, a `Timer.publish` in `ConnectApp.init()` on Mac) — a self-healing backstop, since the event-driven paths alone have no recovery from a dropped message, a send attempted mid-disconnect, or any other race leaving the two sides silently mismatched with nothing to trigger a correction. Safe to call repeatedly: the OR-merge is a no-op whenever the two sides already agree. |
| `dnd.set` | bidirectional | `enabled` (bool) | Requests that the recipient change its own Do Not Disturb / Focus state to match `enabled`. On Mac, handled by shelling out to `shortcuts run "Connect Turn On DND"` / `"Connect Turn Off DND"` (user-created Shortcuts, since macOS has no public API to set Focus state). On Android, handled via `NotificationManager.setInterruptionFilter(...)`, which requires the user to have granted `ACCESS_NOTIFICATION_POLICY` (Notification policy access, a special-access setting) during onboarding. Note: as of this writing neither app's UI actually sends `dnd.set` directly — the only path that triggers it is the `dnd.update` auto-reconciliation above. |
| `clipboard.update` | bidirectional | `text` (string, plain text only — no images/files/rich content in v1), `sourceDeviceId` (uuid, the device whose local clipboard change triggered this message) | Sent whenever the sender's system clipboard changes to a new plain-text value, so the receiver can mirror it into its own clipboard. Both sides must track the last value they wrote to their own clipboard programmatically (in response to a received `clipboard.update`) and skip re-sending when a newly-observed local clipboard value matches it, to avoid an infinite update ping-pong between the two devices. |

# Message Type Registry

This table is the single source of truth for every `type` value that can appear in a Connect wire envelope (see `schema/envelope.schema.json`). Because the Mac app is written in Swift and the Android app is written in Kotlin, there is no shared compiler or shared type definitions between the two codebases — this file is the only thing keeping them in sync.

**Every future feature PR, in either codebase, must add its own `type` entries to this table before shipping.** A message type that isn't registered here should not be sent or handled. Keep `payload fields` precise enough that both sides can implement `Codable` (Swift) / `kotlinx.serialization` (Kotlin) models from this table alone, without needing to read the other language's source.

Wave 1 registered only the message types needed for handshake, presence, and stubbed trust plumbing — that scope boundary is now historical, not current: every feature that's since shipped (clipboard, notifications, DND, media, lock-on-leave, screen mirroring, full mesh trust/roster gossip) has its own registered types below, per this file's own rule that no type may be sent or handled without an entry here first. The rule itself is unchanged going forward — a message type still must not be added until the feature sending/handling it is actually being built — just the "only handshake/presence for now" framing is out of date.

## Per-device feature toggles

Each device has a local, never-transmitted Settings switch per feature, **on by default** (Mac: `FeatureSettings`, Settings window; Android: `FeatureSettings`, Settings screen). A feature that is off on a device means that device takes no part in it: **outgoing** envelopes of its types are never sent (silently skipped at `TransportManager.send`), **incoming** ones are dropped at `MessageRouter` before any handler runs (so no state is applied and no side effect happens), and local triggers that don't go through messages are skipped (Lock-on-Leave's BLE trigger, the clipboard poll, hotspot GATT requests). Relaying *other* devices' envelopes through the mesh is unaffected, and `handshake.*`, `presence.*` and `trust.*` are never gated. Because every message type already has self-healing resync and idempotent handlers (see the repo `CLAUDE.md`), turning a feature back on needs no special step: the next periodic resync or change re-converges the peers.

| `handshake.hello` | mac→android / android→mac / android→android | `noise` (base64 string, Noise_IK handshake message bytes), `deviceName` (string), `deviceType` (`"mac"` \| `"android-phone"` \| `"android-tablet"`), `signingPublicKey` (base64 string, raw Ed25519 signing public key) | First message sent by the initiator to begin a Noise_IK handshake and announce basic device identity. | `handshake.ack` | mac→android / android→mac / android→android | `noise` (base64 string, Noise_IK handshake response bytes), `deviceName` (string), `deviceType` (`"mac"` \| `"android-phone"` \| `"android-tablet"`), `signingPublicKey` (base64 string, raw Ed25519 signing public key) | Responder's reply completing the Noise_IK handshake, carrying its own handshake bytes and device identity. | `presence.online` | bidirectional | *(none)* | Sent once a Noise session is established and the sender considers itself actively connected. | `presence.offline` | bidirectional | *(none)* | Sent as a graceful notice that the sender is about to disconnect (app quit, Bluetooth/Wi-Fi teardown, etc). |
| `presence.heartbeat` | bidirectional | *(none)* | Periodic liveness ping/pong used to detect a silently-dropped connection — one `NWConnection`'s own path-viability tracking (Mac) / a blocking socket read erroring on a clean close (Android) doesn't reliably cover: the peer's Wi-Fi dropping, its OS killing/sleeping the process without a clean close, or a NAT/carrier timeout on a cross-network path can all leave a connection sitting at CONNECTED indefinitely with nothing to trigger reconnection. Previously defined but genuinely unused on both platforms — nothing sent it and nothing ran on a timer. Now: while connected, both sides send this every 20s and independently track the last time *any* frame (not just a heartbeat) was received from the peer; if a heartbeat send fails, or more than 3 intervals (60s) pass with nothing received, the connection is torn down and the normal discovery/reconnect loop takes over. See `TransportManager.startHeartbeatMonitoring` (Mac) / `TransportManager.heartbeatLoop` (Android). |
| `trust.roster_update` | bidirectional | `devices` (array of `{deviceId: uuid, publicKey: base64 string, deviceName: string, deviceType: "mac" \| "android-phone" \| "android-tablet", signingPublicKey: base64 string, optional}`) | Implemented (mesh support). `signingPublicKey` (each entry, optional): the entry's Ed25519 signing public key, when the sender has one on file for it — normally always true for a device paired after the `handshake.hello`/`.ack` `signingPublicKey` field was added, but a receiver applying a gossiped entry for a *new* device it's never heard of skips the entry entirely if this is absent, same as any other required identity field. For an entry the receiver **already** trusts (normally skipped outright to avoid clobbering `addedAt`/metadata — see below), this is the one exception: if the receiver's own row for that `deviceId` is missing a signing key (a pre-existing row from before this field existed) and the gossiped entry has one, just that field is backfilled — `RosterGossipManager.handleRosterUpdate`/`TrustedDevicesStore.backfillSigningPublicKey` (Android), `RosterGossipManager.handleRosterUpdate`/`TrustedDevicesStore.backfillSigningPublicKey` (Mac). Idempotent (a repeat backfill of the same key is a no-op) and never overwrites an already-populated key. Sent **targeted** (`recipientId` = the peer) with this device's full roster (every currently-trusted device, plus itself) immediately after every fresh connection — reconnect or freshly-confirmed pairing — so the newly-connected peer learns everyone this device already knows. Sent **broadcast** whenever a brand-new device is added via pairing (either role — QR-scan/initiator, or QR-display/responder, see `handshake.hello`/`.ack` and `RosterGossipManager`/`ShowQrViewModel` on Android, `RosterGossipManager`/`PairingViewModel` on Mac), so the update reaches the rest of the mesh transitively via the multi-hop flood-forward every device applies to broadcast envelopes (see `docs/wire-protocol.md`'s "Multi-hop relay" section) — this is what makes "pair once, propagate everywhere" work without a dedicated re-gossip step on receipt. Receivers **auto-trust**: every entry except their own `deviceId` is merged into `TrustedDevicesStore` via the existing upsert, with no user confirmation — justified because the gossip only ever arrives over an already-Noise-authenticated connection from an already-trusted device. An entry for a `deviceId` already trusted locally is skipped entirely (never overwritten), so a periodic resync (below) can't clobber a device's own `addedAt`/metadata. **Periodic resync**: both platforms also re-broadcast the full roster every 5 minutes while connected (mirrors `dnd.update`'s periodic resync below) — a self-healing backstop for a dropped targeted/broadcast send. See `docs/adr/0002-device-group-addressing.md` for the original design rationale this implements. |
| `trust.revoke` | bidirectional | `deviceId` (uuid) | Implemented (mesh support). Broadcast to the mesh whenever a device is removed from `TrustedDevicesStore` (the "Forget"/"Remove device" UI action, both platforms) — receivers call the local equivalent of `TrustedDevicesStore.revoke(deviceId)` and tear down any live connection to that device. Not yet handled: an already-revoked device's own re-gossip of itself (out of scope for this pass — a revoked device that somehow still has a live path back into the mesh could theoretically be re-added by a stale `trust.roster_update` from a third device that hasn't heard about the revoke yet; the 5-minute periodic resync above bounds how long that window can last). |
| `screen.start` | mac→android (any viewer→phone) | `sessionId` (string, **required**, UUID minted by the viewer per mirroring attempt), `maxSize` (int px of the long edge, default 1280, clamped 320–2560), `bitRate` (int bps, default 4 000 000, clamped 0.5–20 M), `maxFps` (int, default 30, clamped 1–60), `audio` (bool, default `false`; the Mac viewer sends `true`) | Session setup for on-device screen mirroring (`android/.../features/screenmirror/`, see `android/screen-server/README.md`): the phone pushes the bundled scrcpy v4.1 server jar, launches it at shell UID through Shizuku's `newProcess` (no `MediaProjection` consent dialog), opens a one-viewer WebSocket listener on an ephemeral port, and replies with `screen.ready` (port + token) — or `screen.error` if it can't. The viewer connects `ws://<phone-lan-ip>:<port>`, sends the token as its first message, and gets video / sends control per `ScreenBridge`'s documented framing (Mac viewer: `mac/Gossip/Features/ScreenMirror/`). A `screen.start` without a `sessionId` is ignored (there is no longer a signaling-only form). **Idempotent**: a duplicate `screen.start` for the already-active `sessionId` launches nothing and just re-sends `screen.ready` (this is also the viewer's retry path if a `screen.ready` is lost — the Mac re-sends `screen.start` with the same `sessionId` every 2.5 s until it arrives or 20 s pass); a `screen.start` for a `sessionId` that was already stopped/ended (bounded 64-entry recently-ended cache, mirroring `media.command`'s/`notification.reply`'s pattern) is ignored so a delayed duplicate can't resurrect a finished session; a `screen.start` with a *different* `sessionId` supersedes the active one (the old session is torn down). **Reconciliation**: a session is a one-time, session-scoped event, not persistent configuration, so there is deliberately no periodic resync; instead it self-heals — the phone ends the session (kills the shell-UID processes, closes the listener) when the viewer's WebSocket closes, when no viewer attaches within 30 s of `screen.ready`, or when the Gossip process dies (shell processes exit on stdio EOF — verified), so a lost `screen.stop` cannot leak a running capture. **Security note**: the token travels only inside this Noise-encrypted mesh, and is the sole WebSocket credential (256-bit random, per session, constant-time compared, one viewer allowed); the WebSocket's *video/control payload itself is not encrypted* — anyone who can read the LAN traffic of an attached session can see it, and Noise-over-WebSocket is not yet implemented (see `android/screen-server/README.md`). |
| `screen.stop` | mac→android | `sessionId` (string, **required**) | Ends mirroring: tears down that session if it's the active one and records it in the recently-ended cache (so a later/duplicate `screen.start` for it is ignored — a `screen.stop` that arrives *before* its `screen.start` is also remembered); a `sessionId` that isn't active is otherwise a no-op, so duplicates are harmless; without a `sessionId` it is ignored. Not required for cleanup — the session also ends on viewer disconnect / attach timeout (see `screen.start`). When a session that a viewer had actually attached to ends — for any reason — the phone also puts its screen to sleep (`input keyevent KEYCODE_SLEEP` via Shizuku; the sleep key, not the toggling power key, so an already-dark screen is never switched back on). A session that never got a viewer leaves the screen alone. |
| `screen.ready` | android→mac (**targeted** at the `screen.start` sender) | `sessionId` (string, echoed), `port` (int, the phone's WebSocket listener), `token` (string, 43-char base64url of 32 random bytes — the sole WebSocket credential), `width`/`height` (int, current encoded size), `codec` (`"h264"`) | The phone's reply once the on-device capture is live. The viewer connects to `ws://<phone-lan-ip>:<port>` (it knows the phone's address from the mesh connection), sends `token` as its first (text) message, then receives a text header `{codec,width,height,deviceName,audio}` (`audio` is `null` or `{codec:"raw",sampleRate:48000,channels:2,format:"s16le"}` — `null` when not requested or the device can't capture audio, e.g. Android < 11) followed by binary messages (`0x00` video packet: `u64` BE pts/flags + Annex-B H.264, flag bit 62 = config, bit 61 = key frame; `0x01` size change: `u32` width, `u32` height; `0x02` raw scrcpy device-message bytes; `0x03` audio packet: `u64` pts/flags + interleaved s16le PCM, only when `audio` is non-null — audio is *not* duplicated on the phone's own speaker) and may send raw scrcpy control messages as binary messages. Wire format details live in `ScreenBridge.kt`'s doc comment and `android/screen-server/README.md`. Re-sent (same payload) on every duplicate `screen.start` for the active session — a naturally idempotent re-ack; receivers should treat a repeat as a no-op. |
| `screen.error` | android→mac (**targeted** at the `screen.start` sender) | `sessionId` (string, echoed), `reason` (`"shizuku_unavailable"` \| `"capture_failed"` \| `"feature_disabled"`) | The phone couldn't start on-device capture: Shizuku isn't running / not granted to Gossip (`shizuku_unavailable` — surface a "start Shizuku" hint; Shizuku needs re-activation after every phone reboot), or the scrcpy launch/connect failed (`capture_failed`; details in the phone's logcat tag `ScreenMirror`), or the user turned Screen mirroring off on the phone (`feature_disabled`). The session is already torn down on the phone; the viewer shows the reason and may retry with a *new* `sessionId` (re-using the failed one is ignored by the recently-ended cache). |
| `media.nowplaying` | android→mesh (**broadcast**) | `title` (string), `artist` (string), `artBase64` (string, optional, base64-encoded album art image bytes), `isPlaying` (bool), `positionMs` (int), `durationMs` (int), `packageName` (string, the source app's package name) | Sent by an Android device whenever its active media session's playback state or metadata changes, so every trusted Mac can render a now-playing UI (mesh support: previously targeted at one tracked peer). Each Mac tracks now-playing state per sender (`senderId`), so multiple phones'/tablets' sessions can be shown independently — `MediaControlManager.nowPlayingByDevice`, with a device picker in the menu bar UI when more than one is reporting. `artBase64` is small album-art cover art; per `docs/wire-protocol.md` this is an acceptable exception to the "no base64 blobs" convention only because it is bounded/optional here, not a large binary transfer. **Reconciled, not just event-driven**: `MediaControlBridge.start()` previously only ever published once, at service startup, with nothing tied to the transport's connection state — a Mac that reconnected after being disconnected (or that missed the original publish to any send race) never learned a phone's current now-playing state until the *next* playback/metadata change, possibly a long time or never. Mac never originates this message, so no equivalent sender-side logic is needed there. |
| `media.command` | mac→android, **targeted** (`recipientId`) | `action` (`"play"` \| `"pause"` \| `"next"` \| `"previous"`), `seekMs` (int, optional, only meaningful alongside `play`/`pause` as a seek-to-position request), `commandId` (string, optional, a UUID minted fresh per Mac-side `sendCommand` call — absent only from a peer running a build from before this field existed) | Sent by the Mac to control playback on a *specific* Android device's active media session — targeted at whichever device's now-playing card is currently selected in the menu bar UI (mesh support: previously broadcast, which was only correct because there was ever just one phone; broadcasting a command with more than one device connected would control every phone's session at once). **Idempotency**: `skipToNext()`/`skipToPrevious()` are not naturally idempotent (a duplicate delivery would skip twice) — the Android receiver (`MediaControlBridge.handleCommand`) keeps a bounded recently-handled cache (64 entries) keyed by `commandId` and drops a repeat, per this repo's `CLAUDE.md` idempotency convention; `commandId` is minted once per distinct user action, not reused across genuinely separate presses, only across a retry of the exact same send. |
| `notification.posted` | android→mesh (**broadcast**) | `id` (string, stable per-notification identifier chosen by the Android sender), `appPackage` (string), `appName` (string), `title` (string), `body` (string), `iconBase64` (string, optional, base64 PNG of the source app's **launcher icon**, 96×96 — not the notification's small status-bar glyph, which is a white single-colour shape that rendered as a blank square on the Mac/tablet; the phone encodes each app's icon once and caches it, and omits the field only if the icon can't be loaded), `hasReplyAction` (bool, whether the source notification exposes a `RemoteInput`-bearing action the recipient can reply through), `timestamp` (integer, epoch ms) | **Sent by Android phones only** — a tablet (or other non-phone Android device) never forwards its own notifications (`NotificationListenerImpl` ignores them there); every device type still *receives* and shows phones' notifications. Mirrors an Android status-bar notification onto **every other trusted device in the mesh** — Macs and other Android devices (phones/tablets) alike, not just a single tracked peer (mesh support; previously targeted at one `recipientId`). Excludes `MediaStyle` playback notifications (detected via `EXTRA_MEDIA_SESSION`, the same signal the system itself uses) — those are already covered end to end by `media.nowplaying`/`media.command`. On the Android *receiving* side (new: `NotificationMirrorReceiver`), every locally-posted mirror carries a `dev.vmd1.gossip.app.isMirroredNotification` bundle extra so `NotificationListenerImpl` never re-detects and re-broadcasts its own mirrored copy of someone else's notification — without that guard a phone mirroring a tablet's notification would ping-pong it back out to the whole mesh. Local tracking keys (both platforms) are now `(sourceDeviceId, id)` pairs, not bare `id` — a bare `id` could collide between two different Android devices now that more than one can post into the mesh. |
| `notification.removed` | android→mesh (**broadcast**) | `id` (string, matches the `id` from a prior `notification.posted`) | Tells every other trusted device to dismiss the previously-mirrored notification (the source notification was cleared or dismissed on Android). Broadcast for the same reason as `notification.posted` above. |
| `notification.reply` | mac→android / android→android, **targeted** (`recipientId`) | `id` (string, matches the `id` from a prior `notification.posted`), `text` (string), `attemptId` (string, a UUID minted fresh per reply send — required, no legacy-peer fallback) | Carries an inline reply back to the *specific* device that posted the original notification — not broadcast — so it can be delivered through that notification's `RemoteInput`/`PendingIntent`, round-tripping into the real conversation. With more than one Android device in the mesh, broadcasting this would either misdeliver or no-op on every device except the true owner; `recipientId` is looked up from the `(sourceDeviceId, id)` tracking key mirrored/recorded when the notification was posted. Only valid for notifications where the matching `notification.posted` had `hasReplyAction: true`. The receiving Android device's reply UI (new: `NotificationMirrorReceiver`'s `RemoteInput` action + `NotificationMirrorReplyReceiver`) mirrors Mac's existing inline-reply notification action. **Idempotency (highest-severity gap in this codebase until fixed)**: firing the source app's own `PendingIntent` sends the reply text into a real conversation with a real person outside the app entirely — a duplicate delivery must not fire it twice. `id` can't serve as the dedupe key (it's reused across distinct replies to the same notification), so `attemptId` identifies the *attempt* instead, generated once per user send (`NotificationMirrorManager.sendReply` on Mac, `NotificationMirrorReceiver.sendReply` on Android). `NotificationListenerImpl.handleReply` keeps a bounded recently-handled cache (128 entries, `attemptId`-keyed) and drops a repeat as a no-op, per this repo's `CLAUDE.md` idempotency convention — mirrors the mesh relay's own recently-seen-envelope-`id` cache (`docs/wire-protocol.md`'s "De-duplication" section). |
| `notification.dismiss` | mac→android / android→android, **targeted** (`recipientId`) | `id` (string, matches the `id` from a prior `notification.posted`) | The reverse of `notification.removed`: the user dismissed the mirrored notification on the device that mirrored it, so the original should be cleared too on the *specific* device that posted it (targeted, same reasoning as `notification.reply`). **Not** driven by `UNUserNotificationCenterDelegate`'s dismiss callback on Mac as originally implemented — confirmed directly (unconditional logging at the top of that delegate method, zero deliveries for a swipe-dismissed banner) that macOS does not reliably invoke `didReceive` with `UNNotificationDismissActionIdentifier` for a plain banner swipe/close, unlike iOS. The `didReceive`/`UNNotificationDismissActionIdentifier` path is kept as a fast path in case some interaction or future macOS version does provide it, but the poll is the actual mechanism this depends on. On the posting Android device, handled via `NotificationListenerService.cancelNotification(key)`, the same special capability the service grants for snooze/dismiss features — an ordinary app has no way to dismiss another app's notification. This in turn fires Android's own `onNotificationRemoved` and sends `notification.removed` back out (broadcast); harmless (no-ops removing an already-removed mirrored notification elsewhere), not a ping-pong loop. On the *mirroring* Android device (new: `NotificationMirrorReceiver`), a user swipe-dismissing the mirrored notification fires `NotificationCompat.Builder.setDeleteIntent` → `NotificationMirrorDismissReceiver`, which sends this targeted at the source device — the Android equivalent of Mac's poll-based mechanism, but using the standard Android delete-intent callback since it doesn't have macOS's dismiss-callback unreliability. |
| `dnd.update` | bidirectional | `sourceDeviceId` (uuid), `enabled` (bool), `isInitialSync` (bool, default `false`) | **Broadcast** (mesh support) so every trusted device — not just one peer — reconciles: Mac already sent this `broadcast: true`; Android's send previously set neither `broadcast` nor `recipientId` (harmless under the old single-peer transport, which ignored both and just used whatever the one connection was, but a real bug once more than one peer can be connected — fixed to `broadcast: true`). Sent whenever the sender's own Do Not Disturb / Focus state changes, reporting that new state to the peer. Also auto-reconciled: if the reported `enabled` disagrees with the receiver's own last-known/expected state, the receiver applies it locally the same way it would a `dnd.set` (see below) — so toggling either device mirrors onto the other. Both sides track an `expectedState` (last state they reported or applied) and skip re-sending/re-applying when a newly-observed value already matches it, to avoid an infinite update ping-pong — same convention as `clipboard.update`. On Mac, applying a peer-requested change runs a Shortcut, which itself re-triggers the Shortcuts automation that reports local changes (see `dnd.set` row); both sides also apply a short cooldown after applying a peer state before accepting a new local-change report, as a guard against that automation's delivery timing racing the in-memory state update. On Mac, local changes are detected via a user-configured Shortcuts automation calling the `connect://dnd` URL scheme (see `mac/Gossip/Features/DND/DNDSyncManager.swift`); on Android via a `BroadcastReceiver` for `NotificationManager.ACTION_INTERRUPTION_FILTER_CHANGED` (see `android/app/src/main/kotlin/dev/vmd1/gossip/features/dnd/DndSyncManager.kt`). **`isInitialSync: true`**: sent once by each side on every fresh `CONNECTED` transition (not gated on a local change), carrying that device's real/best-known current state, specifically to reconcile two devices that were apart and may have independently diverged. The receiver does *not* mirror this — it ORs the reported value with its own real/known state and applies the OR'd result if that differs from its own (`enabled=true` wins over `enabled=false` on either side). This must be a merge rather than a mirror: two devices reporting concurrently on connect and blindly mirroring each other would *swap* their states instead of converging. OR is commutative, so both sides converge to the same target independently of message ordering. On Mac (no API to read live Focus state), "real/known state" means the persisted `expectedState` (`UserDefaults`, key `dev.vmd1.gossip.dnd.expectedState`), defaulting to `false` if genuinely never observed; on Android it's a live `NotificationManager.currentInterruptionFilter` read, always available. **Periodic resync**: both sides also re-send an `isInitialSync` report every 60s while connected (`SyncForegroundService.runDndResyncLoop` on Android, a `Timer.publish` in `ConnectApp.init()` on Mac) — a self-healing backstop, since the event-driven paths alone have no recovery from a dropped message, a send attempted mid-disconnect, or any other race leaving the two sides silently mismatched with nothing to trigger a correction. Safe to call repeatedly: the OR-merge is a no-op whenever the two sides already agree. **Mesh scope note**: each device's own OR-merge logic (`expectedState`) is still a single scalar, not a per-sender map — with 3+ devices connected, a receiver ORs each incoming report against its own single running state rather than tracking every peer's last-known state independently. In practice this still converges the same way (OR is commutative/associative regardless of how many devices report, and the 60s periodic resync self-heals any transient disagreement), but it means a device can't currently answer "which specific device(s) have DND on" — only the group's merged result. Confirmed working live with 3 real devices (Mac + phone + tablet) as of this change; revisit if per-device attribution is ever needed. |

On Mac, handled by shelling out to `shortcuts run "Connect Turn On DND"` / `"Connect Turn Off DND"` (user-created Shortcuts, since macOS has no public API to set Focus state). On Android, handled via `NotificationManager.setInterruptionFilter(...)`, which requires the user to have granted `ACCESS_NOTIFICATION_POLICY` (Notification policy access, a special-access setting) during onboarding. Note: as of this writing neither app's UI actually sends `dnd.set` directly — the only path that triggers it is the `dnd.update` auto-reconciliation above. |
| `lock_on_leave.config` | android(phone)→mac/android(tablet), **targeted** (`recipientId`) | `enabled` (bool) | Sent by an Android **phone** whenever the user toggles "Lock this device when I leave" for a specific paired Mac or tablet (in that device's row's settings submenu, phone-side — see `docs/architecture.md`/Feature 4 UI reorg). Only ever sent by a phone and only ever targeted at a non-phone (Mac or tablet): phones are the only BLE-detectable role (`docs/ble-proximity-protocol.md`), so they're the only meaningful trigger for this, and locking another phone isn't supported. The recipient persists this as `TrustedDevice.lockOnLeaveEnabled` on the row for the *sending* phone (keyed by `senderId`), not a new top-level setting — it means "lock me when this specific phone leaves BLE range," so it lives per-pair. No message is needed for the lock trigger itself: the recipient already detects "this trusted phone left BLE range" directly via its own `BLEProximityMonitor` (Mac and tablets are always the BLE central for phones), so a `LockOnLeaveManager` (Mac: `mac/Gossip/Features/Proximity/LockOnLeaveManager.swift`; tablet: `android/.../features/proximity/LockOnLeaveManager.kt`) fires locally off `BLEProximityMonitor.nearbyDeviceIds` transitions, gated on this per-device flag, with an edge-trigger (fires once per range-loss transition, not while continuously out of range) plus a 30s cooldown so it can't repeatedly re-lock a screen the user has manually unlocked. Mac's receiving side needs no equivalent sender-side logic (Mac never originates this message, only the phone does). |

| `clipboard.update` | bidirectional (mesh: broadcast) | `kind` (`"text"` \| `"image"`), `sourceDeviceId` (uuid, the device whose local clipboard change triggered this message); when `kind == "text"`: `text` (string, plain text); when `kind == "image"`: `contentType` (string, always `"image/png"` — both platforms normalize whatever the source pasteboard/clipboard's original representation was, so the wire format is always this one universally-decodable type), `byteLength` (int, the byte length of the raw binary frame that immediately follows this envelope — see `docs/wire-protocol.md`'s "Large binary payloads" section; this envelope sets `hasRawFollowup: true`) | Sent whenever the sender's system clipboard changes to a new value, so every other trusted device in the mesh can mirror it into its own clipboard — plain text (`kind: "text"`) travels as a normal broadcast envelope, relayed transitively through the whole mesh like any other message; an image (`kind: "image"`) also broadcasts its metadata, but the actual bytes travel as a raw follow-up frame, which **is** relayed hop-by-hop (atomically alongside its metadata envelope at every hop) so it still reaches devices with no direct connection to the sender — see `docs/wire-protocol.md`. All devices must track the last value (text or image bytes, whichever) they wrote to their own clipboard programmatically (in response to a received `clipboard.update`) and skip re-sending when a newly-observed local clipboard value matches it, to avoid an infinite update ping-pong. On Mac, an image is normalized to PNG via `NSBitmapImageRep` (TIFF, which AppKit guarantees is always present for image pasteboard content, is the fallback source representation) and written back via `NSPasteboard.setData(_:forType:.png)`; on Android, via `BitmapFactory`/`Bitmap.compress(PNG)` and written back as a `content://` Uri (Android's clipboard image items must be Uri-backed, not raw bytes) through a dedicated `FileProvider`. **Known Android platform limitation, and its Shizuku-conditional fix**: since Android 10, a background app — even a foreground `Service` like `SyncForegroundService` — is denied `ClipboardManager.getPrimaryClip()` reads unless its app currently has window focus (confirmed directly via `ClipboardService`'s own logcat: "Denying clipboard access... application is not in focus"). *Writing* to the clipboard (the receive direction) is unaffected and works from the background normally. An `AccessibilityService`-based workaround was tried and confirmed *not* to grant the exemption on a real Samsung/One UI device. **When Shizuku is connected** (the same optional one-time grant Instant Hotspot uses — see `android/app/src/main/kotlin/dev/vmd1/gossip/features/hotspot/ShizukuManager.kt`; this is a local device capability, not a wire-protocol concept, so it has no message-type row of its own): `ClipboardSyncManager.runBackgroundPollLoop` reads the clipboard every 2s via `features/clipboard/ShizukuClipboardReader.kt`, a Shizuku-brokered shell-UID call to the raw hidden `android.content.IClipboard` interface, which isn't subject to the focus check — confirmed via a real, currently-maintained reference app doing exactly this for the same Mac↔Android clipboard-sync purpose (`github.com/chakri192/clipsyncd`'s `ShizukuClipboard.kt`), and live-verified working in this codebase too. **Text only** — an image copy made while backgrounded still isn't picked up until the app regains focus, since resolving another app's `content://` image Uri cross-process isn't attempted. Shizuku is optional/user-granted, not a hard dependency, same as every other optional-permission feature here (e.g. BLE proximity gracefully no-ops without its permission too): without it, the standard technique real clipboard-manager apps use instead (inspecting the accessibility node tree for a detected copy action rather than calling the Clipboard API) is text-only, fragile across arbitrary apps' UI structures, and not implemented here. **Practical effect now**: with Shizuku granted, Android → mesh text sync works from the background continuously, same as Mac → Android; without it (or for images either way), Android → mesh sync only reliably fires while Connect's own UI is the foregrounded app. Mac → Android sync and Mac ↔ Mac (once relayed) are unaffected either way. See `android/app/src/main/kotlin/dev/vmd1/gossip/features/clipboard/ClipboardSyncManager.kt`'s doc comment. **Reconciled, not just event-driven**: both platforms now also resend whatever is currently on the local clipboard once on every fresh `CONNECTED` transition and every 60s while connected (Mac: `ClipboardSyncManager.start()` + a `resyncTimer`; Android: `ClipboardSyncManager.start()`'s `resendCurrentClipboardIfNeeded()` + `runMediaResyncLoop`-style loop in `SyncForegroundService`), mirroring `dnd.update`'s `isInitialSync`/periodic-resync convention — without this, a local copy made while transiently disconnected (or a send lost to any other race) would never reach a peer until the next actual local clipboard change, possibly never. **Bug fixed (#29)**: the loop-guard (`shouldSend`/`shouldSendImage`) originally only compared against `lastRemoteSetValue` (the last value *received* from a peer), so a periodic resync would re-broadcast an unchanged, locally-originated clipboard value on every tick forever — `lastRemoteSetValue` never matches a value this device itself copied, only one it received. Both platforms now also track `lastSentValue`/`lastSentImageData` (the last value *this device* successfully sent) and skip resending when the current value matches either one — confirmed present and fixed identically on both Mac (`ClipboardSyncManager.swift`) and Android (`ClipboardSyncManager.kt`), even though the bug report was Android-specific; the receiving side re-calling `setPrimaryClip`/`NSPasteboard.setData` on every unnecessary resend is also what surfaced Android's repeated "Copied to clipboard" system toast. |

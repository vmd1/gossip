# Message Type Registry

This table is the single source of truth for every `type` value that can appear in a Connect wire envelope (see `schema/envelope.schema.json`). Because the Mac app is written in Swift and the Android app is written in Kotlin, there is no shared compiler or shared type definitions between the two codebases — this file is the only thing keeping them in sync.

**Every future feature PR, in either codebase, must add its own `type` entries to this table before shipping.** A message type that isn't registered here should not be sent or handled. Keep `payload fields` precise enough that both sides can implement `Codable` (Swift) / `kotlinx.serialization` (Kotlin) models from this table alone, without needing to read the other language's source.

Wave 1 registered only the message types needed for handshake, presence, and stubbed trust plumbing — that scope boundary is now historical, not current: every feature that's since shipped (clipboard, notifications, DND, media, lock-on-leave, screen mirroring, full mesh trust/roster gossip) has its own registered types below, per this file's own rule that no type may be sent or handled without an entry here first. The rule itself is unchanged going forward — a message type still must not be added until the feature sending/handling it is actually being built — just the "only handshake/presence for now" framing is out of date.

## Per-device feature toggles

Each device has a local, never-transmitted Settings switch per feature, **on by default** (Mac: `FeatureSettings`, Settings window; Android: `FeatureSettings`, Settings screen). A feature that is off on a device means that device takes no part in it: **outgoing** envelopes of its types are never sent (silently skipped at `TransportManager.send`), **incoming** ones are dropped at `MessageRouter` before any handler runs (so no state is applied and no side effect happens), and local triggers that don't go through messages are skipped (Lock-on-Leave's BLE trigger, the clipboard poll, hotspot GATT requests). Relaying *other* devices' envelopes through the mesh is unaffected, and `handshake.*`, `presence.*` and `trust.*` are never gated. Because every message type already has self-healing resync and idempotent handlers (see the repo `CLAUDE.md`), turning a feature back on needs no special step: the next periodic resync or change re-converges the peers.

| `handshake.hello` | mac→android / android→mac / android→android | `noise` (base64 string, Noise_IK handshake message bytes). **Identity is inside the Noise payload**, not this envelope: message 1 carries (encrypted, bound to the initiator's static key) JSON `{deviceId: uuid, deviceName, deviceType: "mac" \| "android-phone" \| "android-tablet", signingPublicKey: base64 raw Ed25519, pairingToken?: string}`; the envelope's `senderId` must equal that `deviceId` or the handshake is rejected. | First message sent by the initiator to begin a Noise_IK handshake. See `docs/adr/0003-noise-ik-handshake.md`. Never signed (`sig` absent): there is no session yet. **Responder rules:** (1) a `deviceId` already in the trust store must present exactly the Noise static key it was paired with, else the connection is closed; the `signingPublicKey` from this authenticated payload replaces whatever the row held (it is never taken from gossip). (2) An unknown device is only ever offered to the user while this device is showing its pairing QR (armed for 5 minutes, single use), it must present that QR's `pairingToken` (constant-time compare), and only one confirmation prompt may be open at a time; otherwise the connection is closed. Both screens show a 6-digit code derived from the two static keys (`SHA-256("gossip-pairing-code-v1" ‖ lo ‖ hi)`, first 4 bytes mod 10⁶) for the user to compare. Frames are capped at 16 KiB until the handshake completes (`docs/wire-protocol.md`). Not reconciled: a handshake is per-connection, a reconnect redoes it. **Proof of possession:** Noise message 1 can be replayed by anyone who recorded it, so a *responder* only lets the new connection replace a live one (and sends presence/roster) once the initiator's first transport frame decrypts; the initiator sends `presence.online` immediately after the handshake for this reason. |
| `handshake.ack` | mac→android / android→mac / android→android | `noise` (base64 string, Noise_IK handshake response bytes); the responder's identity (same JSON shape as `handshake.hello`, without `pairingToken`) rides inside the Noise payload of message 2 | Responder's reply completing the Noise_IK handshake. The initiator requires the envelope's `senderId` to equal the authenticated `deviceId`. See `handshake.hello` for the trust, pairing-token and key-binding rules the responder applies. |
| `pair.code.a` | enterer→shower (plaintext, **pre-trust**, first frame on a fresh connection, in place of `handshake.hello`) | `pake` (base64, the enterer's SPAKE2 message) | Pairing by a short code (`desktop/core/src/engine/code_pairing.rs`, `crypto/code_pake.rs`). The **shower** is the new device, which shows an 8-character code (alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, 40 bits) and advertises `pair=1` in its mDNS TXT record; the **enterer** is a device that is already paired, where the user typed the code. SPAKE2 (edwards25519) uses the code as the password and the two device ids as identities, so the code never crosses the network and a recording cannot be brute-forced offline. A shower that is not currently showing a code, whose code expired (5 minutes) or has had 5 wrong attempts, drops the connection without answering; at most 3 exchanges run at once. Code pairing only runs over direct connections, never through the relay. |
| `pair.code.b` | shower→enterer (plaintext, pre-trust) | `pake` (base64, the shower's SPAKE2 message) | Reply to `pair.code.a`. Both sides now derive the same session keys only if they used the same code: HKDF-SHA256 over the SPAKE2 key gives one ChaCha20-Poly1305 key per direction, with a hash of both messages as associated data. |
| `pair.code.proof` | enterer→shower (plaintext envelope, **pre-trust**) | `box` (base64: the enterer's identity JSON `{deviceId, deviceName, deviceType, noisePublicKey, signingPublicKey}` sealed under the enterer-to-shower key) | Opening it proves the enterer typed the right code. A box that does not open is a failed attempt: the shower counts it, tells its UI (`attempts left`) and closes the connection; the fifth invalidates the code. On success the shower trusts the enterer (a direct pairing: it replaces any earlier row and lifts a revocation tombstone) and answers. **Idempotent**: the same device repeating the exchange within 60 s with the correct code (a lost reply) gets the same answer and changes nothing (no second `TrustChanged`, no second success shown); any other device is refused during that window. |
| `pair.code.done` | shower→enterer (plaintext envelope, pre-trust) | `box` (base64: the shower's identity JSON, sealed under the shower-to-enterer key) | Opening it proves the shower used the same code; the enterer trusts it and closes the connection. Both devices then connect the normal way (Noise_IK, no prompt) because each now trusts the other's keys. Because a wrong code only ever shows up as a box that fails to open, an enterer cannot tell a wrong code from a shower that went away and reports both as "rejected". |
| `presence.online` | bidirectional | *(none)* | Sent once a Noise session is established and the sender considers itself actively connected. On Mac this previously silently never sent in practice: called synchronously from `finalizeHandshake`, before the `connectionState` assignment (dispatched via `DispatchQueue.main.async`) had actually taken effect, so `TransportManager.send()`'s old `connectionState`-gated guard always saw the connection as not-yet-connected. Fixed alongside the `dnd.update` initial-sync bug this exact race also caused (see that row) — `send()` no longer gates on `connectionState` at all, only on the actual `noiseSession`/`connection`. |
| `presence.offline` | bidirectional | *(none)* | Sent as a graceful notice that the sender is about to disconnect (app quit, Bluetooth/Wi-Fi teardown, etc). |
| `presence.heartbeat` | bidirectional | *(none)* | Periodic liveness ping/pong used to detect a silently-dropped connection — one `NWConnection`'s own path-viability tracking (Mac) / a blocking socket read erroring on a clean close (Android) doesn't reliably cover: the peer's Wi-Fi dropping, its OS killing/sleeping the process without a clean close, or a NAT/carrier timeout on a cross-network path can all leave a connection sitting at CONNECTED indefinitely with nothing to trigger reconnection. Previously defined but genuinely unused on both platforms — nothing sent it and nothing ran on a timer. Now: while connected, both sides send this every 20s and independently track the last time *any* frame (not just a heartbeat) was received from the peer; if a heartbeat send fails, or more than 3 intervals (60s) pass with nothing received, the connection is torn down and the normal discovery/reconnect loop takes over. See `TransportManager.startHeartbeatMonitoring` (Mac) / `TransportManager.heartbeatLoop` (Android). |
| `trust.roster_update` | bidirectional | `devices` (array of `{deviceId: uuid, publicKey: base64 string, deviceName: string, deviceType: "mac" \| "android-phone" \| "android-tablet", signingPublicKey: base64 string, optional, addedAt: integer ms, optional}`) | Implemented (mesh support). `signingPublicKey` (each entry, optional): the entry's Ed25519 signing public key, when the sender has one on file for it — normally always true for a device paired after the `handshake.hello`/`.ack` `signingPublicKey` field was added, but a receiver applying a gossiped entry for a *new* device it's never heard of skips the entry entirely if this is absent, same as any other required identity field. For an entry the receiver **already** trusts the entry is skipped outright, including its `signingPublicKey`: a signing key is no longer backfilled from gossip (a peer could inject its own for someone else's row); it is learned from that device's own authenticated handshake (`handshake.hello`). `addedAt` (each entry, optional, 0 if absent): when the *sender* added that device to its roster; the sender's own self-entry omits it. A receiver that holds a revocation tombstone for the `deviceId` (see `trust.revoke`) ignores the entry **regardless of `addedAt`** (gossip can never bring a revoked device back, because an introducer could claim any `addedAt`; only pairing it directly again clears the tombstone) and replies to the sender with a targeted `trust.revoke` carrying the tombstone's `revokedAt`. This is what both apps and `gossip-core` implement; an earlier version of this row described an `addedAt` comparison that no code ever performed. Sent **targeted** (`recipientId` = the peer) with this device's full roster (every currently-trusted device, plus itself) immediately after every fresh connection — reconnect or freshly-confirmed pairing — so the newly-connected peer learns everyone this device already knows. Sent **broadcast** whenever a brand-new device is added via pairing (either role — QR-scan/initiator, or QR-display/responder, see `handshake.hello`/`.ack` and `RosterGossipManager`/`ShowQrViewModel` on Android, `RosterGossipManager`/`PairingViewModel` on Mac), so the update reaches the rest of the mesh transitively via the multi-hop flood-forward every device applies to broadcast envelopes (see `docs/wire-protocol.md`'s "Multi-hop relay" section) — this is what makes "pair once, propagate everywhere" work without a dedicated re-gossip step on receipt. Receivers **auto-trust**: every entry except their own `deviceId` is merged into `TrustedDevicesStore` via the existing upsert, with no user confirmation — justified because the gossip only ever arrives over an already-Noise-authenticated connection from an already-trusted device. An entry for a `deviceId` already trusted locally is skipped entirely (never overwritten), so a periodic resync (below) can't clobber a device's own `addedAt`/metadata. **Periodic resync**: both platforms also re-broadcast the full roster every 5 minutes while connected (mirrors `dnd.update`'s periodic resync below) — a self-healing backstop for a dropped targeted/broadcast send. See `docs/adr/0002-device-group-addressing.md` for the original design rationale this implements. **Validation & limits:** `deviceId` must be a UUID, `publicKey`/`signingPublicKey` base64 of exactly 32 bytes, names are cut to 80 characters, at most 64 entries per message are read and a device never trusts more than 64 devices through gossip; invalid entries are skipped. A tombstoned (revoked) device is **never** re-added from gossip regardless of the claimed `addedAt` (a malicious introducer could claim anything) — only pairing it directly again clears the tombstone; the sender of such an entry is sent the `trust.revoke` again. |
| `trust.revoke` | bidirectional | `deviceId` (uuid), `revokedAt` (integer ms, optional — defaults to the envelope `ts`) | Implemented (mesh support). Broadcast to the mesh whenever a device is removed from `TrustedDevicesStore` (the "Forget"/"Remove device" UI action, both platforms) — receivers call the local equivalent of `TrustedDevicesStore.revoke(deviceId, revokedAt)`, tear down any live connection to that device, and keep a sticky **tombstone** (`deviceId` → `revokedAt`, persisted) so gossip cannot quietly re-add it; a later direct pairing of the same device clears the tombstone, and nothing else does (a gossiped introduction never does, however new its `addedAt` claims to be). A revoke naming the receiver's own `deviceId` is ignored. Idempotent (the later `revokedAt` wins; repeats are no-ops). **Reconciliation:** a receiver that sees a tombstoned device introduced in a peer's `trust.roster_update` (the periodic 5-minute resync) sends that peer a targeted `trust.revoke` with the original `revokedAt`, so a peer that missed the one-shot broadcast converges. `revokedAt` is clamped to the receiver's current time so a far-future value can't make a tombstone permanent. |
| `control.session_start` | mac→android, **targeted** (`recipientId`), `ttl: 0` (never relayed) and only ever sent over a **direct** connection | `sessionId` (string, **required**, UUID minted by the Mac per connection attempt), `secret` (string, **required**, base64 of 32 random bytes — the key material for the data channel), `backend` (`"auto"`; reserved for a future backend preference) | Universal Control session setup (`mac/Gossip/Features/UniversalControl/`, `android/.../features/universalcontrol/`). The device launches the bundled scrcpy v4.1 server through Shizuku in **control-only mode** (`video=false audio=false` — nothing is captured, no mirror window opens, the screen is never touched or put to sleep), opens a one-client WebSocket listener on an ephemeral port and replies `control.ready`, or `control.error`. The Mac then dials `ws://<device-lan-ip>:<port>/control` and speaks the **encrypted data channel** (below). Carries key material, which is why it is targeted, `ttl: 0` and never sent unless the Mac has a direct connection to that device (a mesh-only device cannot be controlled). Every (re)connection uses a fresh `sessionId` and `secret`: the channel uses counter nonces, so a key is never reused. **Idempotent**: a duplicate for the active `sessionId` launches nothing and re-sends `control.ready` (also the Mac's retry path for a lost `ready`: it re-sends `session_start` every 2.5 s for up to 15 s); one for a recently-ended `sessionId` (bounded 64-entry cache, the `screen.stop` pattern) is ignored so a delayed duplicate cannot resurrect it; a different `sessionId` supersedes the active session. **Reconciliation**: session-scoped, not persistent configuration, so no periodic resync of the message itself — instead each Mac keeps one *warm* session per placed, directly-connected, enabled device and re-negotiates with exponential backoff whenever it is not ready (that loop is the resync); the device ends a session when the Mac's socket closes, when nobody attaches within 30 s, after 20 s of silence (the Mac pings every 4 s), or when the scrcpy server / Shizuku dies. |
| `control.ready` | android→mac, **targeted**, `ttl: 0` | `sessionId` (echoed), `port` (int), `width`/`height` (int, the display's logical rotation-applied pixel size), `rotation` (0–3), `backend` (`"uhid"`) | The device's listener is up. Naturally idempotent (re-sent for every duplicate `session_start`; a repeat is a no-op). The same display info is repeated authoritatively in the encrypted `hello_ack`, and in `display_info` frames on rotation. |
| `control.error` | android→mac, **targeted**, `ttl: 0` | `sessionId` (echoed), `reason` (`"shizuku_unavailable"` \| `"start_failed"` \| `"bad_secret"` \| `"feature_disabled"`) | The device could not start (or refused) the session. The session is torn down; the Mac backs off and retries with a *new* `sessionId`. |
| `control.end` | bidirectional, **targeted**, `ttl: 0` | `sessionId` | Mac→device: end the session now (also sent when the Mac shelves the device, disables the feature or quits); device→Mac: the session ended on its own (Mac socket vanished, Shizuku died) so the Mac should re-negotiate promptly. Idempotent: ending an unknown/already-ended session is a no-op, and the id goes into the recently-ended cache so a late `session_start` for it is ignored. |
| `screen.start` | mac→android (any viewer→phone) | `sessionId` (string, **required**, UUID minted by the viewer per mirroring attempt), `maxSize` (int px of the long edge, default 1280, clamped 320–2560), `bitRate` (int bps, default 4 000 000, clamped 0.5–20 M), `maxFps` (int, default 30, clamped 1–60), `audio` (bool, default `false`; the Mac viewer sends `true`), `app` (string, optional: an Android package name, e.g. `com.example.notes`; validated against `^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z0-9_]+)+$`, anything else is ignored and the whole screen is mirrored), `appSize` (string `WxH`, default `1080x2340`, only with `app`), `appDpi` (int 120–640, default 420, only with `app`) | **With `app`, the session is an app window** (Android apps as Mac windows): the scrcpy server is launched with `new_display=<appSize>/<appDpi>` so it captures a fresh virtual display, the app is launched on it with scrcpy's `START_APP` control message, the phone's own screen is untouched (and is not put to sleep when the session ends), `vd_system_decorations=false` is passed so no launcher, taskbar or desktop-mode chrome appears on it. Up to 4 app windows run side by side (each its own session, virtual display and Mac window); a fifth makes the oldest one end, and a whole-screen mirror (no `app`) replaces only the previous whole-screen mirror, never an app window. A virtual display can't be resized in place, so the Mac resizes an app window by stopping that session and starting a new one (new `sessionId`) with a different `appSize`; the app reloads. The phone refuses an `app` that is uninstalled, has no launcher or is disabled, with `screen.error` reason `app_unavailable` / `app_disabled`. Session setup for on-device screen mirroring (`android/.../features/screenmirror/`, see `android/screen-server/README.md`): the phone pushes the bundled scrcpy v4.1 server jar, launches it at shell UID through Shizuku's `newProcess` (no `MediaProjection` consent dialog), opens a one-viewer WebSocket listener on an ephemeral port, and replies with `screen.ready` (port + secret) — or `screen.error` if it can't. The viewer connects `ws://<phone-lan-ip>:<port>`, sends a sealed hello carrying the `sessionId` as its first message, and gets video / sends control per `ScreenBridge`'s documented framing (every WebSocket message sealed by `ScreenCipher`) (Mac viewer: `mac/Gossip/Features/ScreenMirror/`; Android viewer: `android/.../features/screenmirror/ScreenViewerActivity.kt` with `ScreenViewerSession`, `WebSocketClient` and `ScreenViewerProtocol`, started from the Mirror button in the paired-devices list — same messages and framing, no new fields). A `screen.start` without a `sessionId` is ignored (there is no longer a signaling-only form). **Idempotent**: a duplicate `screen.start` for the already-active `sessionId` launches nothing and just re-sends `screen.ready` (this is also the viewer's retry path if a `screen.ready` is lost — the Mac re-sends `screen.start` with the same `sessionId` every 2.5 s until it arrives or 20 s pass); a `screen.start` for a `sessionId` that was already stopped/ended (bounded 64-entry recently-ended cache, mirroring `media.command`'s/`notification.reply`'s pattern) is ignored so a delayed duplicate can't resurrect a finished session; a `screen.start` with a *different* `sessionId` supersedes the active one (the old session is torn down). **Reconciliation**: a session is a one-time, session-scoped event, not persistent configuration, so there is deliberately no periodic resync; instead it self-heals — the phone ends the session (kills the shell-UID processes, closes the listener) when the viewer's WebSocket closes, when no viewer attaches within 30 s of `screen.ready`, or when the Gossip process dies (shell processes exit on stdio EOF — verified), so a lost `screen.stop` cannot leak a running capture. **Security note**: `screen.start`, `screen.ready` and `screen.error` are sent **direct-only (`ttl: 0`)**; the 256-bit `secret` travels only inside this Noise-encrypted connection, and the WebSocket's video/audio/control payload is end-to-end encrypted with it (`ScreenCipher`: HKDF-SHA256 per-direction keys, ChaCha20-Poly1305, strictly increasing 8-byte counters so replays are dropped, AAD binds direction and session id; vectors in `schema/screen-cipher-vectors.json`). One viewer per session; connections authenticate independently so a junk connection can't delay the real viewer. |
| `screen.stop` | mac→android | `sessionId` (string, **required**) | Ends mirroring: tears down that session if it's the active one and records it in the recently-ended cache (so a later/duplicate `screen.start` for it is ignored — a `screen.stop` that arrives *before* its `screen.start` is also remembered); a `sessionId` that isn't active is otherwise a no-op, so duplicates are harmless; without a `sessionId` it is ignored. Not required for cleanup — the session also ends on viewer disconnect / attach timeout (see `screen.start`). When a session that a viewer had actually attached to ends — for any reason — the phone also puts its screen to sleep (`input keyevent KEYCODE_SLEEP` via Shizuku; the sleep key, not the toggling power key, so an already-dark screen is never switched back on). A session that never got a viewer leaves the screen alone. |
| `screen.ready` | android→mac (**targeted** at the `screen.start` sender, `ttl: 0`) | `sessionId` (string, echoed), `port` (int, the phone's WebSocket listener), `secret` (string, standard base64 of 32 random bytes — the per-session key for the WebSocket's `ScreenCipher`, carried only here, direct-only `ttl: 0`), `width`/`height` (int, current encoded size), `codec` (`"h264"`) | The phone's reply once the on-device capture is live. The viewer connects to `ws://<phone-lan-ip>:<port>` (it knows the phone's address from the mesh connection), sends a sealed hello carrying the `sessionId` as its first message, then receives a header `{codec,width,height,deviceName,audio}` (a sealed *text-kind* message) (`audio` is `null` or `{codec:"raw",sampleRate:48000,channels:2,format:"s16le"}` — `null` when not requested or the device can't capture audio, e.g. Android < 11) followed by binary messages (`0x00` video packet: `u64` BE pts/flags + Annex-B H.264, flag bit 62 = config, bit 61 = key frame; `0x01` size change: `u32` width, `u32` height; `0x02` raw scrcpy device-message bytes; `0x03` audio packet: `u64` pts/flags + interleaved s16le PCM, only when `audio` is non-null — audio is *not* duplicated on the phone's own speaker) and may send raw scrcpy control messages (sealed binary-kind). Every WebSocket message in both directions is a binary WebSocket message `[u64 BE counter][ChaCha20-Poly1305 ct][tag]` whose plaintext is a kind byte (`0x00` text, `0x01` binary) plus the body. Wire format details live in `ScreenBridge.kt`'s doc comment and `android/screen-server/README.md`. Re-sent (same payload) on every duplicate `screen.start` for the active session — a naturally idempotent re-ack; receivers should treat a repeat as a no-op. |
| `screen.error` | android→mac (**targeted** at the `screen.start` sender, `ttl: 0`) | `sessionId` (string, echoed), `reason` (`"shizuku_unavailable"` \| `"capture_failed"` \| `"feature_disabled"` \| `"app_unavailable"` \| `"app_disabled"`) | The phone couldn't start on-device capture: Shizuku isn't running / not granted to Gossip (`shizuku_unavailable` — surface a "start Shizuku" hint; Shizuku needs re-activation after every phone reboot), or the scrcpy launch/connect failed (`capture_failed`; details in the phone's logcat tag `ScreenMirror`), or the user turned Screen mirroring off on the phone (`feature_disabled`). The session is already torn down on the phone; the viewer shows the reason and may retry with a *new* `sessionId` (re-using the failed one is ignored by the recently-ended cache). |

A pure query with no side effects, so a duplicate just gets the same answer again. |

On Mac, an image is normalized to PNG via `NSBitmapImageRep` (TIFF, which AppKit guarantees is always present for image pasteboard content, is the fallback source representation) and written back via `NSPasteboard.setData(_:forType:.png)`; on Android, via `BitmapFactory`/`Bitmap.compress(PNG)` and written back as a `content://` Uri (Android's clipboard image items must be Uri-backed, not raw bytes) through a dedicated `FileProvider`. **Known Android platform limitation, and its Shizuku-conditional fix**: since Android 10, a background app — even a foreground `Service` like `SyncForegroundService` — is denied `ClipboardManager.getPrimaryClip()` reads unless its app currently has window focus (confirmed directly via `ClipboardService`'s own logcat: "Denying clipboard access... application is not in focus"). *Writing* to the clipboard (the receive direction) is unaffected and works from the background normally. An `AccessibilityService`-based workaround was tried and confirmed *not* to grant the exemption on a real Samsung/One UI device. **When Shizuku is connected** (the same optional one-time grant Instant Hotspot uses — see `android/app/src/main/kotlin/dev/vmd1/gossip/features/hotspot/ShizukuManager.kt`; this is a local device capability, not a wire-protocol concept, so it has no message-type row of its own): `ClipboardSyncManager.runBackgroundPollLoop` reads the clipboard every 2s via `features/clipboard/ShizukuClipboardReader.kt`, a Shizuku-brokered shell-UID call to the raw hidden `android.content.IClipboard` interface, which isn't subject to the focus check — confirmed via a real, currently-maintained reference app doing exactly this for the same Mac↔Android clipboard-sync purpose (`github.com/chakri192/clipsyncd`'s `ShizukuClipboard.kt`), and live-verified working in this codebase too. **Text only** — an image copy made while backgrounded still isn't picked up until the app regains focus, since resolving another app's `content://` image Uri cross-process isn't attempted. Shizuku is optional/user-granted, not a hard dependency, same as every other optional-permission feature here (e.g. BLE proximity gracefully no-ops without its permission too): without it, the standard technique real clipboard-manager apps use instead (inspecting the accessibility node tree for a detected copy action rather than calling the Clipboard API) is text-only, fragile across arbitrary apps' UI structures, and not implemented here. **Practical effect now**: with Shizuku granted, Android → mesh text sync works from the background continuously, same as Mac → Android; without it (or for images either way), Android → mesh sync only reliably fires while Connect's own UI is the foregrounded app. Mac → Android sync and Mac ↔ Mac (once relayed) are unaffected either way. See `android/app/src/main/kotlin/dev/vmd1/gossip/features/clipboard/ClipboardSyncManager.kt`'s doc comment. **Reconciled, not just event-driven**: both platforms now also resend whatever is currently on the local clipboard once on every fresh `CONNECTED` transition and every 60s while connected (Mac: `ClipboardSyncManager.start()` + a `resyncTimer`; Android: `ClipboardSyncManager.start()`'s `resendCurrentClipboardIfNeeded()` + `runMediaResyncLoop`-style loop in `SyncForegroundService`), mirroring `dnd.update`'s `isInitialSync`/periodic-resync convention — without this, a local copy made while transiently disconnected (or a send lost to any other race) would never reach a peer until the next actual local clipboard change, possibly never. **Bug fixed (#29)**: the loop-guard (`shouldSend`/`shouldSendImage`) originally only compared against `lastRemoteSetValue` (the last value *received* from a peer), so a periodic resync would re-broadcast an unchanged, locally-originated clipboard value on every tick forever — `lastRemoteSetValue` never matches a value this device itself copied, only one it received. Both platforms now also track `lastSentValue`/`lastSentImageData` (the last value *this device* successfully sent) and skip resending when the current value matches either one — confirmed present and fixed identically on both Mac (`ClipboardSyncManager.swift`) and Android (`ClipboardSyncManager.kt`), even though the bug report was Android-specific; the receiving side re-calling `setPrimaryClip`/`NSPasteboard.setData` on every unnecessary resend is also what surfaced Android's repeated "Copied to clipboard" system toast. **Content policy** (both platforms, on send *and* receive): content the source app marked sensitive is never sent (macOS `org.nspasteboard.ConcealedType` / `TransientType` / `AutoGeneratedType` and 1Password's marker; Android `android.content.extra.IS_SENSITIVE`, including reads made via Shizuku); text over 1 MiB (UTF-8) and images over 8 MiB, or whose decoded size exceeds 40 million pixels or that don't decode as an image, are dropped; Android deletes received image files from its cache except the one currently on the clipboard. Dropping is a no-op, so a duplicate or resent oversized update changes nothing. **Text is now state**: a device publishes its current clipboard text as the `clipboard.text` state slot (slot value `{"text": string, "sourceDeviceId": uuid}`, `kind: "text"` also present), so the core keeps it correct across reconnects and neither app resends it; a receiver writes a slot change to its own clipboard and the core's `ClipboardGuard` (`desktop/core/src/features/clipboard.rs`) suppresses the echo of that write, a value already published, sensitive content and text over 1 MiB (the slot limit is 1.5 MiB so a JSON-escaped 1 MiB text fits). An **image** is still a `clipboard.update` message with a raw follow-up frame (too large for a slot) and is sent once per copy, not resent periodically. |


## Universal Control data channel (not a mesh message)

**Closed-loop cursor position (`0x18` `cursor_query` Mac→device, `0x86` `cursor_pos` device→Mac).** Android accelerates a relative mouse by an amount that depends on timing (1x below ~500 px/s up to 3x above ~3000 px/s), so the Mac's modelled cursor drifts from the real one and would hand the pointer back too early or late. While the model says the cursor is near an edge that leads to another screen, the Mac sends `cursor_query{token u8}` (at most every 150 ms, one outstanding, 500 ms timeout) and the device replies `cursor_pos{token u8, x u16, y u16, applied u32}`: the real cursor in the display's logical pixels (read from the cursor's SurfaceFlinger layer via Shizuku, offset by the cursor image's hotspot, measured once at the exactly-known entry point) and how many `mouse_move` frames it had applied since the last `enter`. The Mac compares that with its model *as it was after that many moves* (kept in a bounded history) and shifts the model by the difference. Idempotent: a reply with an unknown token or move count is ignored, a lost query or reply just means no correction until the next one, and a device that can't read its cursor sends nothing. Wire format: `18 <token>` and `86 <token> <x:2> <y:2> <applied:4>` (big-endian), asserted byte-for-byte in both test suites.

**Navigation shortcuts (`0x19` `action`, Mac→device).** While the pointer is on a device, ⌘1 / ⌘2 / ⌘3 / ⌘[ (plain ⌘ only) trigger Home / App Switcher / Notifications / Back on it, the same bindings as screen mirroring; the key is not forwarded as input. Wire format `19 <action>` with action 1 = Home, 2 = App Switcher, 3 = Notifications, 4 = Back; unknown values are ignored. The device sends scrcpy `INJECT_KEYCODE` (HOME=3, BACK=4, APP_SWITCH=187) or `EXPAND_NOTIFICATION_PANEL` to its server. One-shot events, not configuration, so no resync; a duplicate delivery is dropped by the channel's replay protection.

Input does **not** ride the mesh (continuous pointer motion cannot tolerate relay latency, and the mesh's best-effort de-duplication is not acceptable for key events). After `control.ready` the Mac opens a WebSocket straight to the device; every WebSocket message is one encrypted frame. Implemented twice, `mac/Gossip/Features/UniversalControl/ControlProtocol.swift` and `android/.../features/universalcontrol/ControlProtocol.kt`, both checked against the shared vectors in `schema/control-test-vectors.json` (generated by Swift, reproduced byte-for-byte by Kotlin).

* **Framing:** `[u64 BE counter][ChaCha20-Poly1305 ciphertext][16-byte tag]`.
* **Keys:** HKDF-SHA256 (ikm = the 32-byte `secret`, salt = UTF-8 `sessionId`, info = `"gossip-control-v1 m2d"` / `"gossip-control-v1 d2m"`), one key per direction. **Nonce:** 4 zero bytes + the counter. **AAD:** `"gossip-control-v1"` + direction byte (1 = m2d, 2 = d2m) + UTF-8 `sessionId`.
* **Replay / duplicate safety (idempotency):** each direction's counter starts at 1 and strictly increases; a receiver drops any frame whose counter is not greater than the last *authenticated* one, so a replayed or duplicated frame is a no-op. A forged frame never advances the counter. A bad tag closes the channel.
* **Auth:** the first message must be an encrypted `hello` carrying the session id (proof the peer holds the secret), answered by `hello_ack`. This replaces the plaintext token the screen-mirroring WebSocket uses.
* **Plaintext frame:** `[u8 kind][payload]`, big-endian. Mac→device: `0x01 hello` (UTF-8 sessionId), `0x10 enter` (`u8 edge` 0 left/1 right/2 top/3 bottom of the *device* the cursor enters through, `u16 position` 0–65535 along that edge), `0x11 leave`, `0x12 mouse_move` (`i16 dx, i16 dy`, device pixels), `0x13 buttons` (`u8` bitmask: 0 primary, 1 secondary, 2 middle, 3 back, 4 forward — absolute state, so a repeat is a no-op), `0x14 scroll` (`i16 dx, i16 dy` in 1/120 notch, +y up, +x right), `0x15 key` (`u16` HID keyboard-page usage, `u8` down/up, `u8` HID modifier bitmask), `0x16 text` (UTF-8), `0x17 ping`. Device→Mac: `0x81 hello_ack`/`0x82 display_info` (`u16 width, u16 height, u8 rotation, u8 backend` — 0 = UHID, 1 = touch overlay, not implemented), `0x84 error` (UTF-8 reason), `0x85 pong`.
* **Device behaviour:** `enter` first wakes the screen if it is off (a `KEYCODE_WAKEUP` press through the scrcpy control channel, queued ahead of the placement; a locked device wakes to its lock screen), then creates a virtual USB-HID mouse and keyboard through scrcpy's UHID control messages (so Android draws a real cursor and delivers real hover/click/scroll/key events) and slams the cursor into the top-left corner (an exact position, since it clamps) before walking it to the entry point; Input frames (`mouse_move`, `buttons`, `scroll`, `key`) are ignored unless the cursor is on the device, even while the devices still exist. `leave` releases held buttons/keys but keeps both devices for a grace period (8 s, `ControlBridge.DEVICE_GRACE_MS`) so crossing back soon after skips their slow creation (cold entry ~0.8 s, warm ~0.2 s); when the period ends without the cursor returning they are destroyed so the cursor disappears and the soft keyboard can return (a device is never destroyed while the cursor is on it, and ending the session destroys them at once). `mouse_move` frames that arrive while an `enter` is still placing the cursor are dropped rather than applied in one burst (still counted as applied for `cursor_pos`). All of these are idempotent (re-`enter` repositions, `leave` when not entered is a no-op). Printable ASCII `text` is injected with scrcpy `INJECT_TEXT`; other text is placed on the device clipboard and pasted (this overwrites the device clipboard). Android applies pointer acceleration to a relative mouse (measured 1.3x–2x on the SM-T500), so the Mac's router models a gain of 1.5 (`PointerRouter.pointerGain`) and relies on the device clamping at its edges.

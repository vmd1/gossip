# Roadmap: Cross-Device Continuity Features vs. Gossip

Apple's Continuity umbrella (Handoff, Universal Clipboard, Instant Hotspot, Sidecar, Universal Control, and the rest) is the primary reference point for this doc, since it's the most complete "every Apple device behaves as one system" feature set to compare against. But Gossip's actual scope — a Mac ↔ Android continuity app, formerly "Connect" — isn't bounded by Apple parity alone: several rows below (Find my device/ring to locate, remote Shortcut triggers, "Open on device", battery sync) come from the closer prior art in this exact Mac/PC↔Android space instead — Join (by Joaoapps), KDE Connect, and Microsoft Phone Link/ChromeOS Phone Hub. This doc lists the known features across those ecosystems and marks which ones Gossip currently replicates, which are plausible future work (with a dependency-ordered build plan), which are deliberately shelved as large standalone efforts, and which are out of scope entirely (either technically infeasible without iOS/Apple-ecosystem infrastructure, or redundant with an existing non-Gossip solution).

Status is based on the current state of `schema/message-types.md`, the `Features/`/`features/` source trees on both platforms, and `docs/ble-hotspot-protocol.md`/`docs/ble-proximity-protocol.md`/`docs/wire-protocol.md`, as of 2026-10-01. Confirmed against current `git log`/source: on-device screen mirroring is still the planned rework (the shipped mirroring row still uses the ADB/`scrcpy` pipeline, `mac/Gossip/Features/ScreenMirror/ADBClient.swift` et al.); the clipboard-resync double-send bug noted in an earlier pass is now fixed on both platforms and documented in `schema/message-types.md`'s `clipboard.update` row (`#29`); nothing else below the Implemented table has any corresponding code yet.

## Legend

- ✅ **Implemented** — shipped in this repo, with a corresponding wire-protocol entry where applicable
- 🔜 **Could implement** — technically feasible on Mac + Android, not yet built, reasonably scoped
- 🗄️ **Shelved** — desirable and feasible, but complicated enough to defer as a large standalone effort
- ❓ **Unsure** — feasible but doubtful value given overlap with what's already covered elsewhere
- 🚫 **Not applicable** — infeasible, redundant with an existing non-Gossip solution, or depends on Apple-ecosystem infrastructure with no Android equivalent

## Build order for "Could implement" 🔜

Ordered by dependency, not just priority — several of these explicitly reuse infrastructure the one(s) before them build. Shelved and Not-applicable items are intentionally excluded from this ordering; pull one in explicitly if it gets reconsidered.

1. **Find my device / ring to locate** — zero dependencies, trivial scope (one targeted message, no new subsystem). A pure quick win; ship it first while bigger infra below is still being designed.
2. **Battery level sync** — same shape as the already-shipped `hotspot.state_update` (periodic broadcast + resync), no dependencies. Another quick win worth front-loading.
3. **"Open on [device]"** — independent, one-shot trigger message; the only item of this group that touches the large-binary-payload convention (for the file variant), otherwise trivial.
4. **On-device screen mirroring rework** — foundational, not just another feature: it's the thing that gives later items something to build on (Universal Control's Android-side input injection, Sidecar's Computer→Tablet streaming pipeline, and the "screen mirroring as a WebSocket viewer" capability the Windows/Linux/Chrome rows already assume). Do this before any of them so nothing downstream is built against the old ADB/scrcpy pipeline only to be reworked again later.
5. **Off-LAN connectivity (tailcat)** — independent of #4, but foundational in its own right: improves reliability for every existing feature when devices aren't on the same LAN, and is a hard prerequisite for the Chrome extension (no raw TCP/BLE from a browser) below.
6. **Universal Control** — depends on #4 for the Android target-side injection path (reuses the Shizuku/`InputManager` mechanism rather than inventing new plumbing).
7. **Sidecar** — depends on both #4 (reversed streaming pipeline, Computer→Tablet instead of Phone→viewer) and #6 (reuses its per-pair arrangement UI and input-relay session wholesale). Must follow both.
8. **Windows app** — launches with mirroring-as-WebSocket-viewer (#4) and a "Computer" input-control story (#6) already designed, instead of retrofitting either.
9. **Linux app** — same rationale as #8; follows it mainly to spread the two large standalone clients apart rather than building both at once.
10. **Chrome extension** — depends on #5 for a browser-reachable transport; benefits from #4 for its mirroring tab.
11. **Continuity Camera** — independent of everything above; nothing else depends on it, so it can slot in wherever capacity allows, but there's no dependency reason to front-load it.
12. **Auto Unlock** — technically independent (the proximity/trust half already ships), ordered last deliberately: it's the most invasive item on this list (a custom PAM/AuthorizationPlugin storing the actual login credential) and deserves a dedicated security review before being scheduled, not just an open slot in the build queue.

## Could implement in the future 🔜

| Feature | Apple's version | Notes |
|---|---|---|
| Continuity Camera | Use iPhone as a Mac webcam/scanner | Android exposes camera2/CameraX APIs; would need a Mac-side virtual camera driver (e.g. CoreMediaIO DAL plugin) and a video-streaming transport separate from the JSON envelope framing — similar to how screen mirroring already sidesteps Noise-encrypted envelopes for bulk data. |
| On-device screen mirroring (replaces the viewer-side ADB/scrcpy pipeline) | iPhone Mirroring | **Android side done and verified on emulators (Android 16 + Android 12); Mac viewer not built; not yet run on real hardware.** The phone runs the capture so the viewer needs no `adb`/`scrcpy`: Gossip bundles the upstream scrcpy v4.1 server jar (Apache 2.0, pinned, SHA-256 in `THIRD_PARTY_NOTICE.txt`), launches it at shell UID through Shizuku's `newProcess` (`CLASSPATH` + `app_process`, scrcpy's own launch), and bridges video + control to one viewer over a token-authenticated WebSocket (`screen.start` with `sessionId` → `screen.ready` with port + token; idempotent, self-ending on viewer disconnect / 30 s no-attach). **Observed, not assumed** (evidence in `android/screen-server/README.md`): the `app_process` `CLASSPATH` launch works (bare `app_process`'s dalvik-cache error is a red herring); mainline Shizuku v13.6.0 works on both OS versions with no fork; **no `MediaProjection` consent dialog**; valid H.264 (576x1280 Constrained Baseline) and scrcpy control injection (POWER key toggled wakefulness) through the WebSocket on both. **One design change forced by testing**: SELinux denies `untrusted_app → shell` abstract-socket `connectto` in both directions (confirmed on Android 16), so the app cannot talk to the server's socket directly; a tiny shell-UID relay class from Gossip's own APK (`ShellRelay`) connects to it and multiplexes over Shizuku's binder stdio. Remaining work: **(1) the Mac viewer** (scrcpy 4.1 client protocol — note its session-packet/flag layout in the README, H.264 decode via VideoToolbox, input mapping; later C#/JS for Windows/Chrome); **(2) encrypt the stream** — today only the token is Noise-protected, the WebSocket payload is plaintext on the LAN (derive an AEAD key from the Noise session or run Noise over the WebSocket); **(3) real-hardware verification** (encoder/SurfaceFlinger differences, sustained-motion bitrate, latency, rotation, slow-viewer backpressure — none measured on emulators); (4) Shizuku "not running" onboarding/state UX (needs re-activation after reboot; reboot persistence untested) and cleanup of `/data/local/tmp/gossip-scrcpy-server.jar`. scrcpy's wire format isn't a stable API, so the jar stays pinned and any bump means re-verifying the format notes. If real hardware disagrees with the emulators, the `screenrecord` pipeline remains the fallback. Supersedes the custom capture server (approach (a)). |
| Off-LAN connectivity (connect when devices aren't on the same network) | *(Continuity works over iCloud; no direct analogue)* | Mesh transport is LAN/BLE only today. **Preferred approach: [tailcat](https://github.com/tailscale/tailcat)** (Tailscale's BSD-3 netcat-over-WireGuard library, Go). No account, tailnet or Android VPN slot. **Addresses are per-session, exchanged via a signaling-only relay**: when a device can't find a peer on the LAN/BLE, it starts a tailcat server, gets a fresh address, and sends it to the peer through the `relay/` server (reshaped from a byte-bridging relay into a small stateless mailbox: `relay.signal` messages capped to ~1 KB and rate-limited, so it can't be used as a tunnel or bandwidth sink). The address is sealed to the recipient with the keys from pairing so the relay only sees ciphertext, and carries a timestamp/session id so stale signals are rejected. The peer dials it and the existing Noise_IK session runs unchanged over the resulting TCP stream; the tailcat server is torn down when the session ends. Nothing is persisted at pairing, so a leaked address is useless afterwards. The signal is a trigger, not stored state: retry with backoff until the tunnel is up, ignore duplicates when a tunnel already exists or is being set up (idempotent per repo convention), and break simultaneous-initiation ties by lowest `deviceId` dials. The peer needs a live relay connection to receive the signal (WebSocket held by the Android foreground service, with the battery cost that implies; FCM would avoid it but adds a Google dependency). Tailcat does STUN-based hole-punching to a direct UDP path and uses Tailscale's DERP relays only to rendezvous and as a fallback, so the traffic and abuse surface sit on DERP, not on infrastructure we run. Keep Noise on top: the tailcat address embeds keys and is effectively a bearer capability for its short lifetime. Caveats: tailcat promises no API/CLI/wire-format stability (pin a version); the default public DERP relays are rate-limited, have no SLA and can be revoked, so support self-hosted DERP; DERP fallback is too slow for screen mirroring (direct paths only); Go needs gomobile on Android and a bundled helper/static lib on Mac; the browser build is DERP-only until WebRTC support, so the Chrome extension would get relayed connections only. The relay still needs hardening either way (neither app connects to `relay/` yet). Current gaps, which apply to the mailbox design too where noted, or fully if we fall back to the old byte-bridging design: `deviceId` in `relay.hello` isn't bound to the signing key (anyone can claim a `deviceId` and kick that device off or squat its bridge request); any fresh keypair can authenticate (open free tunnel); no frame-size cap (`ws` defaults to 100 MiB), rate/bandwidth limits, connection caps or handshake timeout; `pendingRequests` never expire. Fixes: derive `deviceId` from the public key or pin the peer's key in `relay.connect`, match bridges on a pairing-derived rendezvous token, add timeouts/TTLs/size caps/per-key and per-IP quotas, optional shared-secret for self-hosted relays, and keep screen mirroring off it. Update `docs/architecture.md` (currently says the relay is deferred) and `schema/message-types.md` if any message behaviour changes. |
| Windows app | *(no Apple equivalent — extends Gossip beyond macOS, comparable to Microsoft Phone Link)* | A Windows client speaking the same wire protocol (`schema/message-types.md`) as the Mac app: notifications, clipboard, DND, media, trust/pairing and, once on-device mirroring lands, screen mirroring as a pure WebSocket viewer. Like the Mac and Android apps it shares no code with the others, so the protocol docs remain the contract. Not started; toolchain (native WinUI/C# vs. cross-platform) undecided. |

Not started. |
| Find my device / ring to locate | *(no direct Apple equivalent in this project's scope — closer to Join/Find My Phone apps)* | Send a targeted "ring at full volume even if silenced" message (`device.ring`) to a paired phone or Mac. Trivial to add: one more targeted mesh message, no new subsystem. Naturally idempotent (playing an already-playing alarm is a no-op) and needs no reconciliation — it's a one-shot trigger, not persistent state, same category as `screen.start`/`.stop`. |
| "Open on [device]" (push a URL or file to open on another device) | The well-scoped subset of Handoff this project's own Handoff row rules out generically ("no generic per-app activity state") | An Android share-sheet target plus a Mac-side URL/file-open service. One-shot trigger, no reconciliation needed. |

| Auto Unlock (unlock Mac via nearby trusted device) | Apple Watch/iPhone auto-unlock | The proximity half of this is no longer hypothetical — `lock_on_leave` (above) already ships a live BLE proximity monitor, Ed25519-signed device trust, and a working Mac-side privileged-call precedent (WindowServer lock call, and separately the Shizuku-brokered privileged calls Instant Hotspot uses). What's still missing is the *unlock* action itself, which is a materially different problem than lock: there's no equivalent "just call a private API" shortcut for bypassing the login screen the way there was for suspending the session, so this still likely needs a custom PAM/AuthorizationPlugin (`sudo`-installed, storing the actual login credential) — more invasive than anything shipped so far, but the surrounding proximity/trust infrastructure it would sit on top of is now real, not speculative. |
| Universal Control (share one mouse/keyboard across devices) | Universal Control | Scope this around three device *categories*, not specific platforms: **Phone**, **Tablet** (both Android today), and **Computer** (Mac today; Windows/Linux once those apps — already rows above — exist). The split matters because only Computers have an OS-level API to globally capture a physical mouse/keyboard before any app sees it (Mac: `CGEventTap`; Windows: `SetWindowsHookEx`+`SendInput`; Linux: XTest/`uinput`) — Phone/Tablet have no such third-party API, so they can only ever be a control *target*, never a source. Within that constraint: **any Computer can initiate a session targeting any other paired device, including another Computer** — Computer↔Computer is symmetric (either side can grab the other's mouse/keyboard, same as real Universal Control between two Macs), while Computer→Phone/Tablet is one-directional only. Mechanics: a per-device-pair arrangement config (which edge of which screen is adjacent to which device, like the Displays arrangement pane) drives edge-detection on the source; crossing the edge switches the source's event tap from pass-through to consume-and-forward, parking/hiding the local cursor. **Target-side injection differs by category but reuses planned work**: another Computer gets the symmetric equivalent of the source-side APIs (`CGEventPost`/`SendInput`/XTest); a Phone/Tablet has no system cursor concept for touch apps, so this reuses the Shizuku-brokered scrcpy-server control-injection path from the on-device screen mirroring rework above (`InputManager.injectInputEvent` at shell-UID privilege) rather than inventing new Android plumbing — sequencing this after that mirroring rework specifically to inherit it. Worth a short standalone spike: whether Shizuku's shell UID can create a real `/dev/uinput` virtual mouse (SELinux-policy-dependent, varies by device/ROM) for native cursor rendering/hover instead of synthesized taps. New targeted, direct-connection-only mesh types (skip multi-hop relay — continuous cursor movement can't tolerate flood-forward hop latency): `control.session_start`/`.session_end`, `control.cursor_position`, `control.key_event`, `control.scroll`/`.button` (plus a Mac-keycode↔Android-keycode mapping table). **Idempotency is a first-class design constraint here, not an afterthought** — per this repo's handler-idempotency rule, `cursor_position` must carry an **absolute** position, not a relative delta, specifically so a duplicate delivery (mesh retry, dedupe-cache eviction) is a no-op instead of double-moving the cursor; `key_event`/`button` need the same `attemptId` + bounded recently-handled-cache pattern already shipped for `media.command` and `notification.reply`, since a duplicated key-down with no matching key-up is a real stuck-key bug. Mac-side also needs both Accessibility and Input Monitoring TCC grants, which is worth flagging given this project's ad-hoc code signature — ad-hoc signing is exactly the case where TCC grants are known to be flaky/reset on rebuild (same class of friction already hit with the Bluetooth TCC crash). |
| Sidecar (use a Tablet, or another Computer, as a second Computer display) | Sidecar | Revisited after scoping Universal Control above, and now more tractable than originally judged — most of the hard infrastructure is now planned anyway, just pointed in the reverse direction. The on-device screen mirroring rework (above) already builds a Noise-authenticated H.264-over-WebSocket streaming pipeline for *phone → viewer*; Sidecar needs the same pipeline *Computer → Tablet/Computer* instead, and Universal Control above already builds the per-pair arrangement UI (which edge/device a second display logically extends from) and the input-relay session (touch/mouse input on the target flowing back as `control.*` events) that Sidecar needs for the display to actually be interactive, not just a mirror. What's still genuinely new: Mac has no public API to create a real extended-desktop virtual display — the only mechanism (used by Luna Display, Duet, etc.) is the private, undocumented `CGVirtualDisplay` framework, which Apple could change or remove at any point with no warning. That's a real risk, but not a *new category* of risk for this codebase specifically — it's the same tier of bet already made on the private `SACLockScreenImmediate` WindowServer call for Lock-on-Leave, so it's consistent with this project's existing tolerance rather than a step beyond it. Scoping note: a Phone is almost certainly too small to be a useful second display, so this is realistically Computer→Tablet or Computer→Computer only. Given the private-API risk is the only actually-new piece and everything else is reuse, this is close to "Could implement" rather than genuinely shelved — tracked here until `CGVirtualDisplay`'s current behavior is spiked and Universal Control/on-device mirroring have actually shipped to confirm the reuse holds up in practice. |

## Shelved — desirable but complicated 🗄️

| Feature | Apple's version | Why shelved |
|---|---|---|
| Phone call relay (Mac/Tablet/other-phone-as-speakerphone equivalent) | Continuity for calls on Mac | Two layers, with an asymmetric payoff. **Signaling/control** (caller-ID mirror, remote answer/reject/hangup, forcing the ringing phone onto its own speaker) is cheap and fully buildable today on public APIs (`InCallService`/`TelecomManager`, new mesh types e.g. `call.incoming`/`.state_update`/`.answer`/`.reject`/`.hangup`/`.route_to_speaker`) — not what's shelving this. **Real bidirectional call audio** is the hard part: standard cellular call audio is HAL-routed directly between modem and codec, bypassing the app-reachable `AudioFlinger` path entirely, so there's no app-level API (privileged or not) to inject a remote mic as the call's uplink. The one mechanism that actually solves both directions at once is **Bluetooth HFP** — a device completes the Hands-Free (HF) role's Service-Level Connection + SCO audio link, and Android's own audio framework then treats it as a native `TYPE_BLUETOOTH_SCO` endpoint, routing live call audio and remote answer/reject (`ATA`/`AT+CHUP`) through it automatically, same as any car kit or Bluetooth headset — no app-level audio capture/injection needed at all. The ringing phone needs **zero** custom work for this (stock Android already plays the AG role for any connecting HF peripheral). The catch is the *other* device has to implement the HF role: **Android↔Android (tablet, or a second phone) is plausible** — AOSP's hidden `BluetoothHeadsetClient` (`@SystemApi`, `BLUETOOTH_PRIVILEGED`) is built for exactly this (car head units), and is Shizuku-shaped (shell UID), same precedent as the Hotspot fix. **Mac as the HF unit is not** — macOS's `IOBluetooth` stack has only ever played the AG side (pairing with AirPods/headsets as if Mac were the phone); there's no public framework for advertising an HFP HF SDP record and driving the AT command set as a peripheral, and doing it anyway would mean undocumented, unproven `IOBluetoothRFCOMMChannel`/SCO work with no known-working reference. Shelved as a whole rather than split, since the Mac case is almost certainly what matters most here and BHFP doesn't reach it — if revisited, scope it as "phone↔tablet BHFP relay" specifically, with Mac staying on the signaling-only tier (plus, if still wanted, a Shizuku `AudioSource.VOICE_CALL` downlink-only *listen* capture on Mac, the same trick non-root call-recorder apps use, which is one-directional capture and doesn't hit the uplink-injection wall since nothing needs to be injected back into the call for passive listening/recording). A system-signed custom dialer app (i.e. a custom AOSP build) was also considered and rejected: being merely the default-dialer *role* grants nothing extra (no signature permissions), and actually being system-signed would legitimize the Shizuku downlink capture but still doesn't solve uplink injection (that needs board-specific `AudioPatch`/audio-policy HAL config, not an app permission) — and it costs "runs on whatever phone the user already owns," which this project depends on. |

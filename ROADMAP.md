# Roadmap: Cross-Device Continuity Features vs. Gossip

Apple's Continuity umbrella (Handoff, Universal Clipboard, Instant Hotspot, Sidecar, Universal Control, and the rest) is the primary reference point for this doc, since it's the most complete "every Apple device behaves as one system" feature set to compare against. But Gossip's actual scope — a Mac ↔ Android continuity app, formerly "Connect" — isn't bounded by Apple parity alone: several rows below (Find my device/ring to locate, remote Shortcut triggers, battery sync) come from the closer prior art in this exact Mac/PC↔Android space instead — Join (by Joaoapps), KDE Connect, and Microsoft Phone Link/ChromeOS Phone Hub. This doc lists the known features across those ecosystems and marks which ones Gossip currently replicates, which are plausible future work (with a dependency-ordered build plan), which are deliberately shelved as large standalone efforts, and which are out of scope entirely (either technically infeasible without iOS/Apple-ecosystem infrastructure, or redundant with an existing non-Gossip solution).

Status is based on the current state of `schema/message-types.md`, the `Features/`/`features/` source trees on both platforms, and `docs/ble-hotspot-protocol.md`/`docs/ble-proximity-protocol.md`/`docs/wire-protocol.md`, as of 2026-10-19, after release 2.1 (Phase 1 first passes: multi-display, Android → Android mirroring, clipboard history, SMS Messages, phone as trackpad/keyboard and Android apps as Mac windows; 2.0 brought the Rust core, the relay, state slots and pairing by code). Confirmed against current `git log`/source: on-device screen mirroring (with audio) and per-device feature toggles are shipped on both platforms, and the ADB/`scrcpy` mirroring pipeline plus the auto-request Instant Hotspot trigger have been removed; the clipboard-resync double-send bug noted in an earlier pass is now fixed on both platforms and documented in `schema/message-types.md`'s `clipboard.update` row (`#29`); Find my device and battery sync are now shipped on both platforms; the Phase 1 items below carry their own progress notes.

## Legend

- ✅ **Implemented** — shipped in this repo, with a corresponding wire-protocol entry where applicable
- 🔜 **Could implement** — technically feasible on Mac + Android, not yet built, reasonably scoped
- 🗄️ **Shelved** — desirable and feasible, but complicated enough to defer as a large standalone effort
- ❓ **Unsure** — feasible but doubtful value given overlap with what's already covered elsewhere
- 🚫 **Not applicable** — infeasible, redundant with an existing non-Gossip solution, or depends on Apple-ecosystem infrastructure with no Android equivalent

## Build order for "Could implement" 🔜

Completed work is listed under Implemented below. The rest is split into two phases. **Phase 1 completes the Mac ↔ Android pipeline**: everything a Mac and an Android phone or tablet should do together (plus Android ↔ Android mirroring), before any new client platform is started. **Phase 2 builds the other clients** (Windows, Linux, the browser) on the Rust core and the protocol that Phase 1 settles. Ordered by dependency and sensibility: the transport first, then the quick and self-contained items, then the large ones. Shelved and Not-applicable items are excluded; pull one in explicitly if it gets reconsidered.

### Phase 1: complete the Mac ↔ Android pipeline

1. **Iroh transport spike** — evaluate [Iroh](https://www.iroh.computer/) (QUIC with hole punching and a fallback relay, devices identified by Ed25519 keys) as the transport for off-LAN connectivity, built first as a second transport behind the existing link interface and intended to replace the custom relay protocol (the relay is deployed and working, but its launch hardening and keepalive tuning are dropped rather than done, since they would be thrown away). **Measure:** hole-punch success on real carrier networks, battery cost on Android of a held connection (the measurement the relay keepalive work would have done; use `dumpsys batterystats` over a day away from home, and find the carrier's NAT idle timeout), and whether screen mirroring and Universal Control can work off-LAN over a direct Iroh link. **Design points:** keep Noise_IK inside the stream so the conformance vectors and trust model stay the contract; Iroh is async, so it lives in an I/O adapter around the sans-IO core; the browser can only reach it through relay over WebSocket (affects the Chrome extension); the server at `gossip.vmd1.dev` can stay as a self-hosted Iroh relay and keep serving the website. Replacing the transport is a wire break, so a win ships as a major version (3.0). First in Phase 1 because it decides the transport everything after it (Messages, mirroring off-LAN, every Phase 2 client) will use. If the spike loses, keep the existing relay and revisit its launch hardening then. **Progress:** plan and pass bars written in [`docs/plans/iroh-spike.md`](docs/plans/iroh-spike.md); nothing is measured, because it needs days on real carrier networks.
2. **macOS multi-display support** — make every Mac-side feature behave correctly on a Mac with several displays (and with displays attached, removed or rearranged while running). What exists: Universal Control already walks `NSScreen.screens` (`UniversalControlCoordinator`) and the arrangement UI labels a multi-display Mac. What is single-display today: the Universal Control cursor is hidden and restored on `CGMainDisplayID()` only, the mirroring window sizes itself against `NSScreen.main`, and `display.info` carries one size per computer, so the layout model assumes one screen. **Scope:** (1) Universal Control: each Mac display is its own tile in Arrange Devices, edges between a Mac display and a device are per display, hand-over uses the display the cursor is on, and the cursor is hidden and restored on every display; (2) the mirroring window opens on the display the user is on, remembers its display and survives that display being unplugged; (3) hot-plug, sleep/wake and display-rearrangement events refresh the layout and never leave the cursor hidden or captured; (4) the wire side is `displays[]` in `display.info` in place of one size (listed in [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) Phase 0 and not confirmed done), so it changes `schema/message-types.md` and the protocol version and should land before more features depend on the old shape. **Progress (2.1):** the Mac cursor hides and restores on every display, a new mirroring window opens on the display under the mouse, and the Mac publishes an optional `displays[]` in the `control.display` slot; per-display tiles already existed. Hot-plug handling and mirroring-window persistence are not tested: it needs real hardware with two or more displays. Lands before the Android apps-as-windows item, which also has to pick a display.
3. **Android → Android device mirroring** — mirror and control one Android device from another (phone ↔ tablet, or a second phone), as a first-class option next to Mac → Android mirroring. The capture side is already shipped: the Shizuku-launched scrcpy server, the shell-UID relay and the token-authenticated, `ScreenCipher`-encrypted WebSocket stream (`screen.start`/`.ready`/`.stop`/`.error`). What is new is an **Android viewer**: a screen that decodes the H.264 stream with `MediaCodec` onto a `SurfaceView`, plays the audio, and sends touch, keys and Back/Home/Recents back as scrcpy control messages, plus a "Mirror this device" action in the paired-devices list that works from either Android device and gates on the viewer having the Screen mirroring toggle on. Shizuku is needed only on the device being mirrored (the viewer is an ordinary app). Open questions: injecting input from a non-Shizuku viewer's touch screen is just forwarding control messages, but rotation, aspect ratio and keyboard handling on the viewer need design; whether to allow it over the relay (today mirroring is same-network only); and a visible "being mirrored" indicator on the source. Update `schema/message-types.md` only if the existing `screen.*` messages need new fields (they likely do not). **Progress:** built (`ScreenViewerActivity`, `ScreenViewerSession`, `WebSocketClient`, a Mirror button in the device list; no new wire fields), with protocol unit tests and a loopback test of the viewer transport against the real bridge framing that passes on the Samsung SM-S711B. Shipped in 2.1. Not tested end to end between two real devices (only one phone was available), and rotation, keyboard input and a source-side "being mirrored" indicator are not done.
4. **2FA code autofill** — detect one-time codes in mirrored SMS and app notifications on the phone and offer them on the Mac (a clipboard action first, browser autofill later). Builds on the shipped notification mirroring; the open question is detection (pattern matching on-device, never sending notification text anywhere new) and not auto-pasting a code the user didn't ask for.
5. **Clipboard history** — a searchable, pinnable history across devices on top of the shipped text and image clipboard sync, kept on the devices only (never on the relay), with a per-device toggle and an easy clear. Open: how long and how much to keep, and not storing passwords copied from password managers. **Progress (2.1):** built on Mac and Android, on by default and device-local: text history (100 unpinned entries plus pins, `0600` file, sensitive copies skipped), opened from the menu bar or the phone. Image history is not done. The same release hardened clipboard sync: guard markers follow the clipboard, repeated copies are new slot values and unchanged values are not rewritten.
6. **Messages app (SMS/RCS, iMessage-style UI)** — a standalone, installable native app on the Mac with an iMessage-style UI, backed by an **on-device bridge on the Android phone** that signs in to Google Messages with the user's Google Account and speaks the Google Messages for web protocol. The phone holds the only credential and does all talking to Google; the Mac sends and reads through it over the encrypted mesh or the relay, so it works off-LAN and needs no pairing on the Mac. Modelled on how Beeper runs bridges on the device. New message types are needed (see the Could-implement row), so `schema/message-types.md` and the protocol version change with it. Mac-first (a separate window of the Mac app, like the mirroring window); other clients are shelved (see Shelved). **Progress:** a first slice is built: SMS only (no MMS or RCS, no Google account), through a `MessagesBackend` interface on the phone so the Google Messages bridge can replace it, with `messages.*` registered, sends deduplicated by `attemptId`, an iMessage-style Mac window and an off-by-default switch on both ends. **Progress (2.1):** works against a real phone (Samsung SM-S711B) and a Mac: conversation list and history, send, contacts (name suggestions and matching to existing chats; a message to someone with a chat continues it), several phones, a Mac-side cache so the window opens instantly, and a launcher app. A sent message no longer shows twice (Samsung records it itself). The Google Messages/RCS bridge and the account-risk spike are not started, and RCS is skipped for now.
7. **Phone as a Mac peripheral** — use the phone as a microphone, trackpad or keyboard for the Mac, reusing the encrypted control path and virtual input in the other direction. Start with the phone as a remote trackpad/keyboard, which needs only a Mac-side input injector; microphone needs an audio route and a virtual input device on the Mac. **Progress (2.1):** trackpad and keyboard shipped (`peripheral.input` with per-session `seq` dedupe and a `trackpad.status` slot so the phone can say why it does not work). Microphone is not started.
8. **Android apps as individual Mac windows** — run an Android app on a virtual display and show it as its own Mac window with its own Dock entry, instead of mirroring the whole phone. The scrcpy server already bundled supports virtual displays on Android 11 and later, so the capture and input path is reused. **Progress (2.1):** shipped and used on a real phone: up to 4 concurrent app windows on virtual displays, resizing, cached app list and icons, disabled apps are enabled on open (disabled-until-used apps no longer fail), the screen wakes, no system decorations, leaked scrcpy sessions are killed, and closing a window right after opening it no longer launches the app on the phone. Opening an app window no longer raises the "remote access active" notification. Untested on hardware: the black-first-launch fix and the enable-disabled-apps path beyond the apps tried. **Spike first:** apps that refuse secondary displays, per-app audio, keeping the phone's own screen free, launching and closing apps from the Mac, and how long the display survives. Headline item for Phase 1.

### Phase 2: build the other clients

Starts once Phase 1 (including the transport decision in #1) has settled the protocol and feature set, so each new client implements a finished set rather than a moving target. The Rust core is already done and is what these build on.

9. **Windows app** — WinUI 3 (C#) shell over the already-proven core; spike the C# binding (UniFFI vs C ABI) first. Mirroring is a pure WebSocket viewer. Plan phases 3–4. **Before starting, check [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) (Phase 0):** handshake `caps` and `backend: "native"` on `control.*`/`screen.*` were not confirmed done (`displays[]` is handled by #2).
10. **Linux app** — GTK4 + libadwaita in Rust, linking the same core directly; mostly adapters (D-Bus, BlueZ, PipeWire, Wayland/X11). Wayland clipboard and input capture are the known risks. Plan phase 4.
11. **Computer ↔ computer** — computers as sources (media via GSMTC/MPRIS, screen share) and native-backend Universal Control, **Mac↔Mac first** to pin the protocol before Windows/Linux injectors. Most other features already sync between computers through the mesh once Windows and Linux (#9, #10) exist. Plan phases 5–6. 
12. **Sidecar** — now needs #11 (screen share source plus the native control backend) in addition to the shipped streaming pipeline and arrangement UI. Moved out of Phase 1: Mac → Android tablet is the first target (the Mac as the screen source, after the private `CGVirtualDisplay` spike, with touch/mouse input flowing back as `control.*`), then Computer → Computer.
13. **Chrome extension** — depends on the transport decided in #1 for a browser-reachable path (relay over WebSocket); the Rust core compiles to WASM for its Noise implementation; benefits from the shipped screen mirroring for its mirroring tab.
14. **Send tab to phone** — send the current browser tab to a paired device (and back) from the Chrome extension, as a practical subset of Handoff. Needs #13; the phone side is an intent to open the URL.
15. **Continuity Camera** — independent of everything else; nothing depends on it, so it can slot in wherever capacity allows.
16. **Auto Unlock** — technically independent (the proximity/trust half already ships), ordered last deliberately: it's the most invasive item on this list (a custom PAM/AuthorizationPlugin storing the actual login credential) and deserves a dedicated security review before being scheduled, not just an open slot in the build queue.

## Implemented ✅

| Universal Control (share one mouse/keyboard across devices) | Universal Control | Mac → Android (tablets and phones): push the cursor off a screen edge of the Mac and it continues on the device, with the Mac's mouse and keyboard driving it. Lay devices out around your displays in **Settings → Universal Control → Arrange Devices…** (drag and drop, snap to edges, a shelf for unplaced devices); several devices can be placed and are kept connected in parallel, with hand-over device to device. The device gets a real cursor, hover, clicks, scroll and a real keyboard (typing, shortcuts, non-ASCII text) through virtual USB-HID devices created by the bundled scrcpy server in control-only mode (no screen capture, no mirror window, the screen is never touched) over Shizuku. Input travels on its own ChaCha20-Poly1305-encrypted WebSocket straight to the device (`control.session_start`/`.ready`/`.error`/`.end` set it up over the mesh, direct connections only), with replay-safe counters. Escape hatches: Control-Option-Command-Esc, auto-return when a session drops, and cursor restore on quit/sleep/lock. Needs Accessibility and Input Monitoring on the Mac (the app is no longer sandboxed) and Shizuku on the device. Navigation shortcuts while the pointer is on a device: ⌘1 Home, ⌘2 App Switcher, ⌘3 Notifications, ⌘[ Back (same as screen mirroring). Cards in Arrange Devices take the device's real display shape (`display.info`, reconciled), snapping is forgiving, and a banner explains when input capture isn't running (missing Accessibility/Input Monitoring; ad-hoc builds lose these grants on every rebuild). Relative-mouse caveat: Android accelerates a relative mouse by a timing-dependent 1x-3x, so the Mac can't know the cursor position from the deltas it sent; instead, near an edge that leads to another screen it asks the device where its real cursor is (`cursor_query`/`cursor_pos`, read from the SurfaceFlinger cursor layer) and corrects its model, so hand-over happens at the real edge. The virtual devices stay for 8 s after the cursor leaves so crossing back is instant (~0.2 s vs ~0.8 s cold), and motion that arrives while the cursor is being placed is dropped rather than bursting. Known limits: Wi-Fi latency spikes (macOS AWDL channel hopping, a dozing phone radio) show up as mouse stutter and are outside the app's control, and the first crossing after being away still takes ~0.8 s (an attempt to pre-create devices as the cursor nears an edge was tried and removed because it triggered too often). Not built: the touch-overlay fallback backend, and Android → Mac, which is impossible. Wire format: `schema/message-types.md`; E2E: `mac/scripts/run-tablet-e2e.sh`. |

## Open follow-ups from the 2.0 release

Not new features, but work that is known and unscheduled:

- **Android sync service after an app update:** it only restarts when the app is opened or the device boots, so sync stays off after an update until then. Starting a `dataSync` foreground service from a background broadcast is restricted on Android 15 and later, so the fix needs testing on a real device.
- **Mac release signing:** release builds use the self-signed `gossip.vmd1.dev` certificate, which has no team ID, so each update asks for the Keychain password once per item. Local builds can use an Apple Development certificate (`mac/scripts/use-apple-development-signing.sh`, see `docs/building-and-signing.md`), which stops the prompts; releases need a stable team identity (a paid Developer ID, or another way to hold the signing secrets in CI).
- **Code-pairing emulator end-to-end test** (`mac/scripts/e2e-code-pairing.sh`) fails on a developer Mac and did before the 2.0 work; the core and unit tests for code pairing pass.
- **Shizuku "not running" onboarding state:** Shizuku needs re-activation after a phone reboot; surface a clear state instead of a silent mirroring or Universal Control failure.
- **Website cut-over:** point `gossip.vmd1.dev` at the relay-served site (`pages.yml` is already removed).

## Shelved — desirable but complicated 🗄️

| Feature | Apple's version | Why shelved |
|---|---|---|
| Phone call relay (Mac/Tablet/other-phone-as-speakerphone equivalent) | Continuity for calls on Mac | Two layers, with an asymmetric payoff. **Signaling/control** (caller-ID mirror, remote answer/reject/hangup, forcing the ringing phone onto its own speaker) is cheap and fully buildable today on public APIs (`InCallService`/`TelecomManager`, new mesh types e.g. `call.incoming`/`.state_update`/`.answer`/`.reject`/`.hangup`/`.route_to_speaker`) — not what's shelving this. **Real bidirectional call audio** is the hard part: standard cellular call audio is HAL-routed directly between modem and codec, bypassing the app-reachable `AudioFlinger` path entirely, so there's no app-level API (privileged or not) to inject a remote mic as the call's uplink. The one mechanism that actually solves both directions at once is **Bluetooth HFP** — a device completes the Hands-Free (HF) role's Service-Level Connection + SCO audio link, and Android's own audio framework then treats it as a native `TYPE_BLUETOOTH_SCO` endpoint, routing live call audio and remote answer/reject (`ATA`/`AT+CHUP`) through it automatically, same as any car kit or Bluetooth headset — no app-level audio capture/injection needed at all. The ringing phone needs **zero** custom work for this (stock Android already plays the AG role for any connecting HF peripheral). The catch is the *other* device has to implement the HF role: **Android↔Android (tablet, or a second phone) is plausible** — AOSP's hidden `BluetoothHeadsetClient` (`@SystemApi`, `BLUETOOTH_PRIVILEGED`) is built for exactly this (car head units), and is Shizuku-shaped (shell UID), same precedent as the Hotspot fix. **Mac as the HF unit is not** — macOS's `IOBluetooth` stack has only ever played the AG side (pairing with AirPods/headsets as if Mac were the phone); there's no public framework for advertising an HFP HF SDP record and driving the AT command set as a peripheral, and doing it anyway would mean undocumented, unproven `IOBluetoothRFCOMMChannel`/SCO work with no known-working reference. Shelved as a whole rather than split, since the Mac case is almost certainly what matters most here and BHFP doesn't reach it — if revisited, scope it as "phone↔tablet BHFP relay" specifically, with Mac staying on the signaling-only tier (plus, if still wanted, a Shizuku `AudioSource.VOICE_CALL` downlink-only *listen* capture on Mac, the same trick non-root call-recorder apps use, which is one-directional capture and doesn't hit the uplink-injection wall since nothing needs to be injected back into the call for passive listening/recording). A system-signed custom dialer app (i.e. a custom AOSP build) was also considered and rejected: being merely the default-dialer *role* grants nothing extra (no signature permissions), and actually being system-signed would legitimize the Shizuku downlink capture but still doesn't solve uplink injection (that needs board-specific `AudioPatch`/audio-policy HAL config, not an app permission) — and it costs "runs on whatever phone the user already owns," which this project depends on. |
| Messages on every device (shared Messages session) | *(Messages on Mac, iPad and iPhone share one account)* | Making the Messages app (#6) available on all clients, not just the Mac. The phone-hosted design in #8 already gives the shape of the answer, since any client could read and send through the phone over the mesh, with no pairing of its own. Shelved for now, so #6 ships Mac-first. Revisit when the Phase 2 clients exist, mainly to decide history sync (cached per device or fetched on demand) and which clients get the app. |

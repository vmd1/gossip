# Roadmap: Cross-Device Continuity Features vs. Gossip

Apple's Continuity umbrella (Handoff, Universal Clipboard, Instant Hotspot, Sidecar, Universal Control, and the rest) is the primary reference point for this doc, since it's the most complete "every Apple device behaves as one system" feature set to compare against. But Gossip's actual scope — a Mac ↔ Android continuity app, formerly "Connect" — isn't bounded by Apple parity alone: several rows below (Find my device/ring to locate, remote Shortcut triggers, battery sync) come from the closer prior art in this exact Mac/PC↔Android space instead — Join (by Joaoapps), KDE Connect, and Microsoft Phone Link/ChromeOS Phone Hub. This doc lists the known features across those ecosystems and marks which ones Gossip currently replicates, which are plausible future work (with a dependency-ordered build plan), which are deliberately shelved as large standalone efforts, and which are out of scope entirely (either technically infeasible without iOS/Apple-ecosystem infrastructure, or redundant with an existing non-Gossip solution).

Status is based on the current state of `schema/message-types.md`, the `Features/`/`features/` source trees on both platforms, and `docs/ble-hotspot-protocol.md`/`docs/ble-proximity-protocol.md`/`docs/wire-protocol.md`, as of 2026-10-01. Confirmed against current `git log`/source: on-device screen mirroring (with audio) and per-device feature toggles are shipped on both platforms, and the ADB/`scrcpy` mirroring pipeline plus the auto-request Instant Hotspot trigger have been removed; the clipboard-resync double-send bug noted in an earlier pass is now fixed on both platforms and documented in `schema/message-types.md`'s `clipboard.update` row (`#29`); Find my device and battery sync are now shipped on both platforms; nothing else in the Could-implement table has any corresponding code yet.

## Legend

- ✅ **Implemented** — shipped in this repo, with a corresponding wire-protocol entry where applicable
- 🔜 **Could implement** — technically feasible on Mac + Android, not yet built, reasonably scoped
- 🗄️ **Shelved** — desirable and feasible, but complicated enough to defer as a large standalone effort
- ❓ **Unsure** — feasible but doubtful value given overlap with what's already covered elsewhere
- 🚫 **Not applicable** — infeasible, redundant with an existing non-Gossip solution, or depends on Apple-ecosystem infrastructure with no Android equivalent

## Build order for "Could implement" 🔜

Ordered by dependency, not just priority — several of these explicitly reuse infrastructure the one(s) before them build. Shelved and Not-applicable items are intentionally excluded from this ordering; pull one in explicitly if it gets reconsidered.

1. ~~**Find my device / ring to locate**~~ — **Done** (see Implemented).
2. ~~**Battery level sync**~~ — **Done** (see Implemented); it is in the reconciliation loop (on change, on connect, every 60s).
3. ~~**On-device screen mirroring rework**~~ — **Done** (see Implemented). It delivered the Shizuku-launched scrcpy server, the shell-UID relay and the token-authenticated WebSocket bridge that items 4 and 5 reuse for input injection and streaming; the Mac viewer, audio and a borderless window shipped with it. Still open and relevant to those items: encrypting the stream end to end (only the session token is Noise-protected today), a Shizuku "not running" onboarding state, and an Android-side viewer/other-platform viewers.
4. ~~**Universal Control**~~ — **Done for Mac → Android** (see Implemented); Computer↔Computer and Windows/Linux sources remain future work, on the same platform-neutral layout model and encrypted frame codec.
5. **Protocol 2.0 and conformance** — the prerequisite for everything below; see [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) (Phase 0). Noise handshake/transport test vectors (none exist yet; Mac and Android interoperate on hand-rolled constructions), `windows`/`linux` device types, handshake `caps`, role-bound messages generalized (`media.*`, `display.info` → `displays[]`, `backend: "native"` on `control.*`/`screen.*`), camera-less pairing, a dial tie-break for computer↔computer, relay vectors (topic derivation, join signature and proof, routing header), and a conformance CI job. A wire break, so `VERSION` goes to `2.0`.
6. **Rust core, adopted on Mac and Android** — `desktop/core`, sans-IO, passing the shared vectors, adopted one layer per release (crypto/framing, envelope/mesh, trust/reconcile, pure feature logic) behind a fallback flag with old and new run side by side in CI. Mac and Android are the proving ground; Windows and Linux inherit a verified core. Plan Phase 1. **Status: the core itself is built and verified (`desktop/core`, 83 tests, interop-tested against the Mac app's real Swift code); bindings and the layer-by-layer adoption in the apps are what remains.**
7. **Public relay (off-LAN connectivity)** — a topic-hub relay: one WebSocket per device, pairwise Noise sessions routed by tag, hard abuse limits, built into the core after #6 is verified. Design and abuse model in [`docs/plans/relay.md`](docs/plans/relay.md); plan Phase 2. Independent of Windows/Linux but foundational for the Chrome extension.
8. **Windows app** — WinUI 3 (C#) shell over the already-proven core; spike the C# binding (UniFFI vs C ABI) first. Mirroring is a pure WebSocket viewer. Plan phases 3–4.
9. **Linux app** — GTK4 + libadwaita in Rust, linking the same core directly; mostly adapters (D-Bus, BlueZ, PipeWire, Wayland/X11) once #8 exists. Wayland clipboard and input capture are the known risks. Plan phase 4.
10. **Computer ↔ computer** — computers as sources (media via GSMTC/MPRIS, screen share) and native-backend Universal Control, **Mac↔Mac first** to pin the protocol before Windows/Linux injectors. Most other features already sync between computers through the mesh once #8/#9 exist. Plan phases 5–6.
11. **Sidecar** — now needs #10 (screen share source plus the native control backend) in addition to #3/#4's streaming pipeline and arrangement UI.
12. **Chrome extension** — depends on #7 for a browser-reachable transport; the Rust core compiles to WASM for its Noise implementation; benefits from #3 for its mirroring tab.
13. **Continuity Camera** — independent of everything above; nothing else depends on it, so it can slot in wherever capacity allows, but there's no dependency reason to front-load it.
14. **Auto Unlock** — technically independent (the proximity/trust half already ships), ordered last deliberately: it's the most invasive item on this list (a custom PAM/AuthorizationPlugin storing the actual login credential) and deserves a dedicated security review before being scheduled, not just an open slot in the build queue.

## Implemented ✅

| Feature | Apple's version | Gossip equivalent |
|---|---|---|
| Universal Control (share one mouse/keyboard across devices) | Universal Control | Mac → Android (tablets and phones): push the cursor off a screen edge of the Mac and it continues on the device, with the Mac's mouse and keyboard driving it. Lay devices out around your displays in **Settings → Universal Control → Arrange Devices…** (drag and drop, snap to edges, a shelf for unplaced devices); several devices can be placed and are kept connected in parallel, with hand-over device to device. The device gets a real cursor, hover, clicks, scroll and a real keyboard (typing, shortcuts, non-ASCII text) through virtual USB-HID devices created by the bundled scrcpy server in control-only mode (no screen capture, no mirror window, the screen is never touched) over Shizuku. Input travels on its own ChaCha20-Poly1305-encrypted WebSocket straight to the device (`control.session_start`/`.ready`/`.error`/`.end` set it up over the mesh, direct connections only), with replay-safe counters. Escape hatches: Control-Option-Command-Esc, auto-return when a session drops, and cursor restore on quit/sleep/lock. Needs Accessibility and Input Monitoring on the Mac (the app is no longer sandboxed) and Shizuku on the device. Navigation shortcuts while the pointer is on a device: ⌘1 Home, ⌘2 App Switcher, ⌘3 Notifications, ⌘[ Back (same as screen mirroring). Cards in Arrange Devices take the device's real display shape (`display.info`, reconciled), snapping is forgiving, and a banner explains when input capture isn't running (missing Accessibility/Input Monitoring; ad-hoc builds lose these grants on every rebuild). Relative-mouse caveat: Android accelerates a relative mouse by a timing-dependent 1x-3x, so the Mac can't know the cursor position from the deltas it sent; instead, near an edge that leads to another screen it asks the device where its real cursor is (`cursor_query`/`cursor_pos`, read from the SurfaceFlinger cursor layer) and corrects its model, so hand-over happens at the real edge. The virtual devices stay for 8 s after the cursor leaves so crossing back is instant (~0.2 s vs ~0.8 s cold), and motion that arrives while the cursor is being placed is dropped rather than bursting. Known limits: Wi-Fi latency spikes (macOS AWDL channel hopping, a dozing phone radio) show up as mouse stutter and are outside the app's control, and the first crossing after being away still takes ~0.8 s (an attempt to pre-create devices as the cursor nears an edge was tried and removed because it triggered too often). Not built: the touch-overlay fallback backend, and Android → Mac, which is impossible. Wire format: `schema/message-types.md`; E2E: `mac/scripts/run-tablet-e2e.sh`. |

| Per-device feature toggles (Settings) | *(no Apple equivalent — System Settings → per-feature Continuity switches come closest)* | **Done.** A Settings window on Mac (menu bar → Settings…, which also now holds Pair New Device, Do Not Disturb sync setup and Run Setup Again) and a Settings screen on Android, each with an on/off switch per feature — Clipboard, Do Not Disturb, Notifications, Media controls, Screen mirroring, Lock on leave, Instant Hotspot — **all on by default**, stored locally and never sent over the wire. Off means that device takes no part in the feature: its outgoing messages are skipped at `TransportManager.send`, incoming ones are dropped at `MessageRouter` before any handler runs, and local triggers that bypass messages (Lock-on-Leave's BLE trigger, the clipboard poll, hotspot GATT requests) are skipped; a phone whose Screen mirroring is off answers `screen.start` with `screen.error` `feature_disabled`. | iPhone Mirroring (screen mirroring) | iPhone Mirroring app (macOS 15+) | **Done.** On-device capture, no `adb`/`scrcpy` install: the phone runs a bundled scrcpy v4.1 server (Apache 2.0, pinned, SHA-256 in `THIRD_PARTY_NOTICE.txt`) at shell UID via Shizuku's `newProcess`, a small shell-UID relay bridges its sockets (SELinux blocks app↔shell sockets directly), and an authenticated one-viewer WebSocket carries H.264 video, scrcpy control messages and raw PCM audio (`screen.start`/`stop`/`ready`/`error`, idempotent, self-ending on viewer disconnect). No MediaProjection consent dialog. The old bundled adb/scrcpy pipeline and QR wireless-debugging pairing were removed entirely — no fallback. **Open:** the stream is end-to-end encrypted (`ScreenCipher`, ChaCha20-Poly1305, keyed by a per-session secret that only travels inside the Noise mesh; see `screen.start`/`screen.ready` in `schema/message-types.md`); Shizuku needs re-activation after a phone reboot (surface a clear state); rotation/slow-viewer backpressure and clipboard paste are unverified or unbuilt. ## Could implement in the future 🔜

| Feature | Apple's version | Notes |
|---|---|---|
| Continuity Camera | Use iPhone as a Mac webcam/scanner | Android exposes camera2/CameraX APIs; would need a Mac-side virtual camera driver (e.g. CoreMediaIO DAL plugin) and a video-streaming transport separate from the JSON envelope framing — similar to how screen mirroring already sidesteps Noise-encrypted envelopes for bulk data. |
| Off-LAN connectivity (connect when devices aren't on the same network) | *(Continuity works over iCloud; no direct analogue)* | Mesh transport is LAN/BLE only today. **Planned: a public topic-hub relay, built into the Rust core** after the core is verified on Mac and Android (build order #6, #7). Every device in a mesh joins one topic on the relay with a single WebSocket; each pair still runs its own Noise_IK session, carried in frames the relay routes by a cleartext per-topic tag, so there is no group key and `trust.revoke` is unchanged. The relay is an untrusted router: it never decrypts, never opens outbound connections, and can reach nothing except other members of the same topic, so it can drop or delay traffic and see metadata but cannot read, forge or splice it. LAN stays preferred; bulk features (`screen.*`, `control.*`) refuse relayed paths. A mesh-level `topicSecret` and `epoch` are distributed by a reconciled `mesh.topic` message, and a revoke bumps the epoch. Because there are no accounts, abuse resistance is layered: Ed25519-signed joins bound to the relay origin, a topic proof so a leaked id isn't enough, proof of work for new keys, per-IP and per-topic limits, a small frame cap with a token-bucket and daily quota, bounded queues, a circuit breaker that sheds new topics first, uniform errors, `wss`-only with pinned hosts, a version gate and kill switch, plus fuzzing, load tests and ops tooling before launch. The relay's identity is the Ed25519 key hash, so no `deviceId` migration is needed. Tailcat/WireGuard direct paths remain a possible later optimization. Full design, limits and open questions: [`docs/plans/relay.md`](docs/plans/relay.md). `docs/architecture.md` still says the relay is deferred and `schema/message-types.md` needs `mesh.topic`; both are updated when the work ships. |
| Windows app | *(no Apple equivalent — extends Gossip beyond macOS, comparable to Microsoft Phone Link)* | A Windows client speaking the same wire protocol (`schema/message-types.md`) as the Mac app: notifications, clipboard, DND, media, trust/pairing and, now that on-device mirroring has shipped, screen mirroring as a pure WebSocket viewer. Like the Mac and Android apps it shares no code with the others, so the protocol docs remain the contract. Not started. Plan: [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) — the Rust core (adopted on Mac and Android first) plus a native WinUI 3 (C#) shell. |
| Linux app | *(no Apple equivalent — extends Gossip beyond macOS, comparable to KDE Connect)* | A Linux desktop client speaking the same wire protocol (`schema/message-types.md`) as the Mac and Android apps: notifications, clipboard, DND, media (MPRIS) and trust/pairing, plus screen mirroring as a WebSocket viewer now that on-device mirroring has shipped. Shares no code with the other apps, so the protocol docs remain the contract. Likely integration points are D-Bus (notifications, MPRIS), BlueZ (BLE proximity/hotspot) and the Wayland/X11 clipboard, which differ by desktop environment. Not started. Plan: [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) — GTK4 + libadwaita in Rust linking the shared core; packaging (Flatpak/AppImage/deb) undecided. |
| Chrome extension | *(no Apple equivalent — a lightweight, OS-agnostic client)* | A browser-based client for machines where installing an app isn't possible or desirable (Windows, Linux, ChromeOS, a work laptop): notification mirroring/reply, clipboard sync and, via on-device mirroring, a screen-mirroring tab (WebSocket + WebCodecs decode). Needs a transport that works from a browser (no raw TCP sockets / BLE proximity from a service worker — likely the relay in `relay/` or WebSocket direct to the phone) and a Noise implementation in JS. Not started. |
| Auto Unlock (unlock Mac via nearby trusted device) | Apple Watch/iPhone auto-unlock | The proximity half of this is no longer hypothetical — `lock_on_leave` (above) already ships a live BLE proximity monitor, Ed25519-signed device trust, and a working Mac-side privileged-call precedent (WindowServer lock call, and separately the Shizuku-brokered privileged calls Instant Hotspot uses). What's still missing is the *unlock* action itself, which is a materially different problem than lock: there's no equivalent "just call a private API" shortcut for bypassing the login screen the way there was for suspending the session, so this still likely needs a custom PAM/AuthorizationPlugin (`sudo`-installed, storing the actual login credential) — more invasive than anything shipped so far, but the surrounding proximity/trust infrastructure it would sit on top of is now real, not speculative. |
| Sidecar (use a Tablet, or another Computer, as a second Computer display) | Sidecar | Revisited after scoping Universal Control above, and now more tractable than originally judged — most of the hard infrastructure is now planned anyway, just pointed in the reverse direction. The on-device screen mirroring rework (above) already builds a token-authenticated (not yet Noise-encrypted) H.264-over-WebSocket streaming pipeline for *phone → viewer*; Sidecar needs the same pipeline *Computer → Tablet/Computer* instead, and Universal Control above already builds the per-pair arrangement UI (which edge/device a second display logically extends from) and the input-relay session (touch/mouse input on the target flowing back as `control.*` events) that Sidecar needs for the display to actually be interactive, not just a mirror. What's still genuinely new: Mac has no public API to create a real extended-desktop virtual display — the only mechanism (used by Luna Display, Duet, etc.) is the private, undocumented `CGVirtualDisplay` framework, which Apple could change or remove at any point with no warning. That's a real risk, but not a *new category* of risk for this codebase specifically — it's the same tier of bet already made on the private `SACLockScreenImmediate` WindowServer call for Lock-on-Leave, so it's consistent with this project's existing tolerance rather than a step beyond it. Scoping note: a Phone is almost certainly too small to be a useful second display, so this is realistically Computer→Tablet or Computer→Computer only. Given the private-API risk is the only actually-new piece and everything else is reuse, this is close to "Could implement" rather than genuinely shelved — tracked here until `CGVirtualDisplay`'s current behavior is spiked and Universal Control/on-device mirroring have actually shipped to confirm the reuse holds up in practice. |

## Shelved — desirable but complicated 🗄️

| Feature | Apple's version | Why shelved |
|---|---|---|
| Phone call relay (Mac/Tablet/other-phone-as-speakerphone equivalent) | Continuity for calls on Mac | Two layers, with an asymmetric payoff. **Signaling/control** (caller-ID mirror, remote answer/reject/hangup, forcing the ringing phone onto its own speaker) is cheap and fully buildable today on public APIs (`InCallService`/`TelecomManager`, new mesh types e.g. `call.incoming`/`.state_update`/`.answer`/`.reject`/`.hangup`/`.route_to_speaker`) — not what's shelving this. **Real bidirectional call audio** is the hard part: standard cellular call audio is HAL-routed directly between modem and codec, bypassing the app-reachable `AudioFlinger` path entirely, so there's no app-level API (privileged or not) to inject a remote mic as the call's uplink. The one mechanism that actually solves both directions at once is **Bluetooth HFP** — a device completes the Hands-Free (HF) role's Service-Level Connection + SCO audio link, and Android's own audio framework then treats it as a native `TYPE_BLUETOOTH_SCO` endpoint, routing live call audio and remote answer/reject (`ATA`/`AT+CHUP`) through it automatically, same as any car kit or Bluetooth headset — no app-level audio capture/injection needed at all. The ringing phone needs **zero** custom work for this (stock Android already plays the AG role for any connecting HF peripheral). The catch is the *other* device has to implement the HF role: **Android↔Android (tablet, or a second phone) is plausible** — AOSP's hidden `BluetoothHeadsetClient` (`@SystemApi`, `BLUETOOTH_PRIVILEGED`) is built for exactly this (car head units), and is Shizuku-shaped (shell UID), same precedent as the Hotspot fix. **Mac as the HF unit is not** — macOS's `IOBluetooth` stack has only ever played the AG side (pairing with AirPods/headsets as if Mac were the phone); there's no public framework for advertising an HFP HF SDP record and driving the AT command set as a peripheral, and doing it anyway would mean undocumented, unproven `IOBluetoothRFCOMMChannel`/SCO work with no known-working reference. Shelved as a whole rather than split, since the Mac case is almost certainly what matters most here and BHFP doesn't reach it — if revisited, scope it as "phone↔tablet BHFP relay" specifically, with Mac staying on the signaling-only tier (plus, if still wanted, a Shizuku `AudioSource.VOICE_CALL` downlink-only *listen* capture on Mac, the same trick non-root call-recorder apps use, which is one-directional capture and doesn't hit the uplink-injection wall since nothing needs to be injected back into the call for passive listening/recording). A system-signed custom dialer app (i.e. a custom AOSP build) was also considered and rejected: being merely the default-dialer *role* grants nothing extra (no signature permissions), and actually being system-signed would legitimize the Shizuku downlink capture but still doesn't solve uplink injection (that needs board-specific `AudioPatch`/audio-policy HAL config, not an app permission) — and it costs "runs on whatever phone the user already owns," which this project depends on. |

## Not applicable 🚫

| Feature | Apple's version | Why |
|---|---|---|

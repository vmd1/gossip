# Roadmap: Cross-Device Continuity Features vs. Gossip

Apple's Continuity umbrella (Handoff, Universal Clipboard, Instant Hotspot, Sidecar, Universal Control, and the rest) is the primary reference point for this doc, since it's the most complete "every Apple device behaves as one system" feature set to compare against. But Gossip's actual scope — a Mac ↔ Android continuity app, formerly "Connect" — isn't bounded by Apple parity alone: several rows below (Find my device/ring to locate, remote Shortcut triggers, battery sync) come from the closer prior art in this exact Mac/PC↔Android space instead — Join (by Joaoapps), KDE Connect, and Microsoft Phone Link/ChromeOS Phone Hub. This doc lists the known features across those ecosystems and marks which ones Gossip currently replicates, which are plausible future work (with a dependency-ordered build plan), which are deliberately shelved as large standalone efforts, and which are out of scope entirely (either technically infeasible without iOS/Apple-ecosystem infrastructure, or redundant with an existing non-Gossip solution).

Status is based on the current state of `schema/message-types.md`, the `Features/`/`features/` source trees on both platforms, and `docs/ble-hotspot-protocol.md`/`docs/ble-proximity-protocol.md`/`docs/wire-protocol.md`, as of 2026-10-12, after release 2.0 (the Rust core, the relay, state slots and pairing by code all shipped in it). Confirmed against current `git log`/source: on-device screen mirroring (with audio) and per-device feature toggles are shipped on both platforms, and the ADB/`scrcpy` mirroring pipeline plus the auto-request Instant Hotspot trigger have been removed; the clipboard-resync double-send bug noted in an earlier pass is now fixed on both platforms and documented in `schema/message-types.md`'s `clipboard.update` row (`#29`); Find my device and battery sync are now shipped on both platforms; nothing else in the Could-implement table has any corresponding code yet.

## Legend

- ✅ **Implemented** — shipped in this repo, with a corresponding wire-protocol entry where applicable
- 🔜 **Could implement** — technically feasible on Mac + Android, not yet built, reasonably scoped
- 🗄️ **Shelved** — desirable and feasible, but complicated enough to defer as a large standalone effort
- ❓ **Unsure** — feasible but doubtful value given overlap with what's already covered elsewhere
- 🚫 **Not applicable** — infeasible, redundant with an existing non-Gossip solution, or depends on Apple-ecosystem infrastructure with no Android equivalent

## Build order for "Could implement" 🔜

Ordered by dependency, not just priority — several of these explicitly reuse infrastructure the one(s) before them build. Shelved and Not-applicable items are intentionally excluded from this ordering; pull one in explicitly if it gets reconsidered.

1. ~~**Find my device / ring to locate**~~ — **Done** (see Implemented).
2. ~~**Battery level sync**~~ — **Done** (see Implemented); it is a state slot reconciled by the core (on change, on connect, digest repair every 60 s).
3. ~~**On-device screen mirroring rework**~~ — **Done** (see Implemented). It delivered the Shizuku-launched scrcpy server, the shell-UID relay and the token-authenticated WebSocket bridge that items 4 and 5 reuse for input injection and streaming; the Mac viewer, audio and a borderless window shipped with it. Still open and relevant to those items: encrypting the stream end to end (only the session token is Noise-protected today), a Shizuku "not running" onboarding state, and an Android-side viewer/other-platform viewers.
4. ~~**Universal Control**~~ — **Done for Mac → Android** (see Implemented); Computer↔Computer and Windows/Linux sources remain future work, on the same platform-neutral layout model and encrypted frame codec.
5. ~~**Protocol 2.0 and conformance**~~ — **Done, shipped as `VERSION` 2.0 (release `v2.0`, 2026-10-11).** Delivered: Noise handshake/transport vectors (`schema/noise-ik-vectors.json`, regenerated and compared in CI), `windows`/`linux` device types in the core, pairing without a camera (8-character code, see Implemented), the lowest-`deviceId`-dials rule over the relay, the relay vectors and a conformance CI job. Every device must run 2.0: the per-feature update messages became state slots (below), which is a wire break. **Not confirmed done in this pass, check [`docs/plans/desktop-clients.md`](docs/plans/desktop-clients.md) (Phase 0) before the Windows work:** handshake `caps`, `displays[]` for multi-monitor computers, and `backend: "native"` on `control.*`/`screen.*`.
6. ~~**Rust core, adopted on Mac and Android**~~ — **Done.** `desktop/core` (sans-IO, about 180 tests, with Swift and Kotlin binding smoke tests in CI) now runs the transport, the relay client, trust and reconciliation, state sync, code pairing and the feature logic on both apps; the old native Noise sessions were deleted. In the core: DND, battery, hotspot state, lock on leave, clipboard rules, display info, media and notification state, find-my-device, the BLE beacon tag, the hotspot GATT codec, the stream cipher for screen mirroring and Universal Control, the control frame codec, the screen layout and the pointer router. **Still native by design (OS-specific):** HID key tables and reports, the Mac event tap and cursor warp, the Android cursor locator, the screen-mirroring pipeline, and the Shizuku, Bluetooth and Accessibility glue.
7. ~~**Public relay (off-LAN connectivity)**~~ — **Done and deployed; launch hardening remains.** The relay server (`relay/`, TypeScript) runs at `gossip.vmd1.dev` from the multi-arch Docker image `ghcr.io/vmd1/gossip/relay` (amd64 and arm64, built on native runners by `relay-image.yml`; `latest` follows `main`), which also serves the project website at its root (`SITE_DIR`), replacing GitHub Pages once the domain is cut over. Apps resolve the relay as custom URL, else a polled relay directory (`https://api.vmd1.dev/v1/config/gossip`, published; polled at launch, every 6 h plus or minus 10 %, with 1 to 30 minute failure backoff and at most one extra poll per 10 minutes on relay connect failure), else the built-in default. Relay settings (on/off and custom address) sync across the mesh in the `relay.config` state slot, newest edit wins. A peer rejoining the relay is redialed at once (no stale backoff), and a device whose link dropped no longer shows as reachable through the mesh. Design and abuse model in [`docs/plans/relay.md`](docs/plans/relay.md) and [`docs/relay-threat-model.md`](docs/relay-threat-model.md). **Remaining before it counts as launched:** the threat model's checklist (load tests that exercise each limit, alerts on every reject reason, a spending cap, a staged rollout), and the battery work in 7a. Independent of Windows/Linux but foundational for the Chrome extension.
   - **7a. Relay battery and keepalive testing** — measure what holding the relay socket costs on Android, then tune. Today a held relay link is touched about every 20 s: the relay server and both clients ping every 30 s (`PING_INTERVAL_MS`, `RelayConnection.PING_INTERVAL_SECONDS`, Mac `pingInterval`), the core heartbeats every live link every 20 s with a 60 s timeout (`HEARTBEAT_INTERVAL_MS`), and state digests go out every 60 s. The Android socket is only held while a paired device lacks a LAN link (parked 30 s after all are direct). **Test:** compare battery use (`dumpsys batterystats` over a day away from home) with the relay off, on at today's intervals, and on with longer ones; and find the idle timeout of the carrier's NAT, since a longer interval only helps up to that point. **Candidate changes** (from how [ntfy](https://docs.ntfy.sh/subscribe/phone/) does it, which pings every 3 min from the client and lets the OS signal dead links): much longer relay pings, no separate 20 s heartbeat on relayed links (the WebSocket ping already covers liveness), and fast failure detection from the default-network callback and TCP close, so a quiet link is not what notices a dead one. That last part matters because the Mac already takes about a minute to notice a phone that vanished without closing its socket. Firebase push is out (it needs a cloud service); a partial wake lock is not currently held and should only be added if measurements show missed pushes.
8. **Windows app** — WinUI 3 (C#) shell over the already-proven core; spike the C# binding (UniFFI vs C ABI) first. Mirroring is a pure WebSocket viewer. Plan phases 3–4.
9. **Linux app** — GTK4 + libadwaita in Rust, linking the same core directly; mostly adapters (D-Bus, BlueZ, PipeWire, Wayland/X11) once #8 exists. Wayland clipboard and input capture are the known risks. Plan phase 4.
10. **Computer ↔ computer** — computers as sources (media via GSMTC/MPRIS, screen share) and native-backend Universal Control, **Mac↔Mac first** to pin the protocol before Windows/Linux injectors. Most other features already sync between computers through the mesh once #8/#9 exist. Plan phases 5–6.
11. **Sidecar** — now needs #10 (screen share source plus the native control backend) in addition to #3/#4's streaming pipeline and arrangement UI.
12. **Chrome extension** — depends on #7 for a browser-reachable transport; the Rust core compiles to WASM for its Noise implementation; benefits from #3 for its mirroring tab.
13. **Continuity Camera** — independent of everything above; nothing else depends on it, so it can slot in wherever capacity allows, but there's no dependency reason to front-load it.
14. **Auto Unlock** — technically independent (the proximity/trust half already ships), ordered last deliberately: it's the most invasive item on this list (a custom PAM/AuthorizationPlugin storing the actual login credential) and deserves a dedicated security review before being scheduled, not just an open slot in the build queue.

## Open follow-ups from the 2.0 release

Not new features, but work that is known and unscheduled:

- **Relay launch hardening** (see #7) and **battery and keepalive testing** (7a).
- **Android sync service after an app update:** it only restarts when the app is opened or the device boots, so sync stays off after an update until then. Starting a `dataSync` foreground service from a background broadcast is restricted on Android 15 and later, so the fix needs testing on a real device.
- **Mac release signing:** release builds use the self-signed `gossip.vmd1.dev` certificate, which has no team ID, so each update asks for the Keychain password once per item. Local builds can use an Apple Development certificate (`mac/scripts/use-apple-development-signing.sh`, see `docs/building-and-signing.md`), which stops the prompts; releases need a stable team identity (a paid Developer ID, or another way to hold the signing secrets in CI).
- **Code-pairing emulator end-to-end test** (`mac/scripts/e2e-code-pairing.sh`) fails on a developer Mac and did before the 2.0 work; the core and unit tests for code pairing pass.
- **Website cut-over:** point `gossip.vmd1.dev` at the relay-served site and remove `pages.yml`.

## Shelved — desirable but complicated 🗄️

| Feature | Apple's version | Why shelved |
|---|---|---|
| Phone call relay (Mac/Tablet/other-phone-as-speakerphone equivalent) | Continuity for calls on Mac | Two layers, with an asymmetric payoff. **Signaling/control** (caller-ID mirror, remote answer/reject/hangup, forcing the ringing phone onto its own speaker) is cheap and fully buildable today on public APIs (`InCallService`/`TelecomManager`, new mesh types e.g. `call.incoming`/`.state_update`/`.answer`/`.reject`/`.hangup`/`.route_to_speaker`) — not what's shelving this. **Real bidirectional call audio** is the hard part: standard cellular call audio is HAL-routed directly between modem and codec, bypassing the app-reachable `AudioFlinger` path entirely, so there's no app-level API (privileged or not) to inject a remote mic as the call's uplink. The one mechanism that actually solves both directions at once is **Bluetooth HFP** — a device completes the Hands-Free (HF) role's Service-Level Connection + SCO audio link, and Android's own audio framework then treats it as a native `TYPE_BLUETOOTH_SCO` endpoint, routing live call audio and remote answer/reject (`ATA`/`AT+CHUP`) through it automatically, same as any car kit or Bluetooth headset — no app-level audio capture/injection needed at all. The ringing phone needs **zero** custom work for this (stock Android already plays the AG role for any connecting HF peripheral). The catch is the *other* device has to implement the HF role: **Android↔Android (tablet, or a second phone) is plausible** — AOSP's hidden `BluetoothHeadsetClient` (`@SystemApi`, `BLUETOOTH_PRIVILEGED`) is built for exactly this (car head units), and is Shizuku-shaped (shell UID), same precedent as the Hotspot fix. **Mac as the HF unit is not** — macOS's `IOBluetooth` stack has only ever played the AG side (pairing with AirPods/headsets as if Mac were the phone); there's no public framework for advertising an HFP HF SDP record and driving the AT command set as a peripheral, and doing it anyway would mean undocumented, unproven `IOBluetoothRFCOMMChannel`/SCO work with no known-working reference. Shelved as a whole rather than split, since the Mac case is almost certainly what matters most here and BHFP doesn't reach it — if revisited, scope it as "phone↔tablet BHFP relay" specifically, with Mac staying on the signaling-only tier (plus, if still wanted, a Shizuku `AudioSource.VOICE_CALL` downlink-only *listen* capture on Mac, the same trick non-root call-recorder apps use, which is one-directional capture and doesn't hit the uplink-injection wall since nothing needs to be injected back into the call for passive listening/recording). A system-signed custom dialer app (i.e. a custom AOSP build) was also considered and rejected: being merely the default-dialer *role* grants nothing extra (no signature permissions), and actually being system-signed would legitimize the Shizuku downlink capture but still doesn't solve uplink injection (that needs board-specific `AudioPatch`/audio-policy HAL config, not an app permission) — and it costs "runs on whatever phone the user already owns," which this project depends on. |

## Unsure ❓

| Feature | Apple's version | Why uncertain |
|---|---|---|
| Watch-based notification/DND source | Apple Watch as the Focus/DND source of truth | Deliberately limited scope: WearOS already mirrors virtually everything happening on the paired Android phone onto the watch, so a Gossip-side Watch/WearOS integration would likely be redundant with what WearOS itself already surfaces rather than adding new capability. Only worth revisiting for something WearOS doesn't already replicate from the phone. |

## Not applicable 🚫

| Feature | Apple's version | Why |
|---|---|---|
| File transfer (AirDrop-style) | AirDrop | Was previously attempted and explicitly removed (see commit `998d08d`, "remove file transfer"). Not needed going forward — NearDrop already covers AirDrop-style transfer to/from Apple devices. |
| SMS/RCS relay (Text Message Forwarding equivalent) | Forward iPhone texts to Mac and reply | Not needed — Google Messages already provides web/desktop access to Android SMS/RCS. |
| Handoff (resume an in-progress task on another device) | Handoff | Not feasible: would require per-app "activity" state with no generic Android equivalent, and no practical way to hand off arbitrary third-party app state the way Apple's `NSUserActivity`-based mechanism does. |
| Continuity Markup / Sketch (annotate a doc from iPad) | Continuity Markup, Continuity Sketch | Not a useful fit — low value relative to the effort of a Mac-initiated "send this document to be annotated" flow with real-time drawing sync and per-app (Mail, Preview, etc.) integration. |
| iCloud Keychain / password AutoFill handoff | Continuity-based Keychain/password AutoFill | Pointless to build here — dedicated password managers already solve this, and taking it on would add security/trust liability well beyond the notification/media/clipboard scope of this app. |
| Continuity between Apple Watch and iPhone specifically (e.g. unlocking apps, Wallet handoff) | Watch↔iPhone Continuity | Entirely dependent on WatchOS/iOS pairing, which this project (Mac↔Android) has no path into. |
| eSIM/Continuity phone-number features tied to carrier + iCloud account | Continuity (calls/SMS via iCloud-linked Apple ID) | The call relay idea above is listed as feasible; the Apple-specific "same number across all your Apple devices via iCloud" mechanism itself is not portable, and SMS/RCS specifically is already covered by Google Messages. |
| Shared system clipboard for files/styled content | Universal Clipboard (files, styled text) | Universal Clipboard won't be expanded further — text and image (PNG) sync (already shipped, see Implemented) is the intended scope; file references and styled/RTF text are out of scope going forward. |
| Auto-hotspot on WAN-loss (timeout-triggered, no manual toggle) | Instant Hotspot's automatic fallback | **Built, then removed by product decision.** A WAN-reachability probe plus a per-device switch and per-phone eligibility flag could auto-request a hotspot after being offline for a minute; it was deleted from both platforms (manager, probe, UI switches, stored flag) so Instant Hotspot is manual-only. Not planned to return. |
